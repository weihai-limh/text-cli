# text-cli Progressive Deployment Navigation

text-cli adopts progressive deployment — ramping up on demand from the zero-dependency protocol layer to full skill-as-a-service. Each tier is a complete endpoint; upgrading is additive, not a replacement.

Source code lives under `src/skeleton/`, grouped by runtime (base / copilot / service / endpoint / bypass-service). Each group contains `docs/README_zh.md`. Artifacts under `deploy/` are generated by `scripts/build-all.py`.

## Tier Navigation

| Tier | Directory | Runtime | Notes |
|:---:|------|------|------|
| A0 | `A0-protocol/` | — | Protocol spec + zero-dependency call examples (shell/call.sh, call.ps1 + python/call.py + js/call.js) |
| A1 | `A1-skill/` | — | Agent Skill definition layer (SKILL + tc-web-chat + phase-kernel) |
| A2 | `A2-copilot/` | copilot (:20260) | Local AI orchestration — cmd engine + Skill Bridge + package management |
| A3 | `A3-service/` | service (:28050) | Platform management core — package install/uninstall + instruction discovery + skill exposure + NoCode engine |
| A4 | `A4-paths/` | service (:28050) | Path orchestration — instruction-chain declaration + delegated dispatch + fallback substitution + loop iteration (map) |
| A5 | `A5-endpoint/` | gateway (:29050) | Integration endpoint gateway — Access Token auth + IP blacklist + time-window rate limiting + aggregate forwarding (Docker + Cloudflare Workers) |
| A6 | `A6-sql/` | service (:28050) | SQLite persistence layer — secret management + quota tracking + async tasks |
| A7 | `A7-mcp/` | service (:28050) | MCP bidirectional bridge — config-driven exposure + mcporter tool invocation |
| A8 | `A8-discovery/` | service (:28050) | Aggregation entry — multi-provider fallback chain, first in the dispatch pipeline (incl. local instruction discovery: query/search/match + whitelist) |
| A9 | `A9-advanced/` | service (:28050) | Facade abstraction + full accumulation endpoint — skill-as-a-service; AI can publish advanced instructions (incl. aggregate fallback + multi-source unification + federated mesh) |

> Note: A8's "instruction discovery" refers to the **runtime-local query/search/match of installed instruction packages** (instruction-level route discovery), not a centralized discovery service; the project does not operate a centralized discovery service — see `docs/ecological-partners_zh.md` Non-goal.
> A9's "federated mesh" is a delegation model (invoke, not peer-to-peer interoperability) — multi-hop following is off by default and deployers may enable it explicitly in yaml; availability-first by design, not a security recommendation; cross-operator discovery requires a self-built layer — see the ecosystem doc Non-goal.

## Bypass Service

Non-Python runtimes, parallel to but independently deployed from the tier navigation, and not participating in the A2→A9 accumulation chain. `bypass-service/` is synced by `build-all.py` in passthrough mode, covering five forms: local package executors (pypi / npm), edge-compute gateway (cloudflare D1), generic JS logic layer (tc-js-skeleton), and dsh hosting (dsh-tc-runtime / dsh-tc-bridge).

| Tier | Platform | Directory | Runtime | Notes |
|:---:|------|------|------|------|
| BYPASS | cloudbase | `bypass-service/cloudbase/` | Cloud function | Tencent Cloud SCF — gateway routing + instruction dispatch (Node.js / wx-server-sdk) |
| BYPASS | cloudflare | `bypass-service/cloudflare/` | Edge compute | Cloudflare Workers D1 multi-function edition — executable packages in D1 + restricted execution + single Service-token loop |
| BYPASS | dsh | `bypass-service/dsh/` | dsh hosting | dsh-tc-runtime (Cordis plugin set) / dsh-tc-bridge (tc instruction-consumption seam) |
| BYPASS | tc-js | `bypass-service/tc-js-skeleton/` | Generic JS | Generic JS logic layer source (12 textcli-core-* components, onion layering) |
| BYPASS | pypi / npm / core-c / core-rust | `bypass-service/pypi/` `bypass-service/npm/` `bypass-service/text-cli-core-c/` `bypass-service/text-cli-core-rust/`  | Package executor | Multilingual instruction-package loaders — load and execute directly in Python / js / c / rust environments |

> See `bypass-service/docs/INDEX_en.md`.

## Standard Runtime (Python-based) Typical Distribution Directories

A2, A3, and A9 are the three typical runtimes deployed directly. The project provides their quick-deploy packages in `container`, `win`, `linux`, and `mac` forms.

A2 is a standalone copilot; A3 accumulates copilot (A2) + the base service. A4, A6, A7, A8, and A9 each add content as incremental accumulation layers over the service, tier by tier. A9 is the full accumulation endpoint — it contains the complete copilot + service.

```text
deploy/A2-copilot/                  # A2 standalone copilot — local AI orchestration
└── copilot/                        # runtime root (generated by build-all.py from src/skeleton/copilot/A2-copilot/)
    ├── text-cli-copilot.py          # entry — python text-cli-copilot.py → :20260
    ├── core.py                      # instruction engine + route parsing
    ├── handlers/                    # instruction handlers (key / skill_bridge / package_manager / codec / adapters)
    ├── packages/                    # package management placeholder
    ├── config/                      # routing preferences / key routing / Skill Bridge config
    ├── whitelist_loader.py
    └── auxiliary_config.json

deploy/A3-service/                  # A3 accumulation layer — A2 capabilities + platform management core
├── copilot/                        # inherited from A2 accumulation (copilot runtime)
├── service/                        # A3 body — platform management service
│   ├── main.py                     # entry — python main.py → :28050
│   ├── requirements.txt
│   ├── core/                       # core engine (auth / parser / registry / response / mcp_dispatch)
│   ├── handlers/                   # instruction handlers (installer / skill_endpoint / proxy / nocode, etc.)
│   ├── config/                     # service manifest / system schema / webhook routing / prompt templates
│   └── packages/                   # package management


deploy/A9-advanced/                 # A9 accumulation endpoint — copilot + service + MCP + aggregation
├── copilot/                        # inherited from A2 accumulation
├── service/                        # full A3–A8 service-layer accumulation
│   ├── main.py                     # entry — python main.py → :28050
│   ├── requirements.txt
│   ├── core/                       # as above, incl. identity_context / stream_subscriber_registry
│   ├── handlers/                   # full handler set (incl. quota_handler / task_manager / mcp_handler)
│   ├── config/                     # full config (incl. mcporter / path_messages / multilingual)
│   └── packages/
├── MCPservice/                     # from A7 — MCP bridge service (server.py → :9020)
│   ├── server.py
│   └── manage.sh
├── aggregate/                      # from A8 — aggregate routing table
│   ├── map.json
│   └── web.json

```

> **Accumulation rule**: A3 automatically includes A2's `copilot/`; A9 automatically includes all layers A2–A8. Files with the same name in later layers override earlier ones. The `copilot/` and `service/` subdirectories are members of `build-all.py`'s `SKELETON_SUBDIRS` whitelist, ensuring correct pass-through.

## How to Deploy

**Deployment is the `deploy/` directory.** Pick the target tier, enter the corresponding directory, and start the service:

```bash
# Deploy A2 local Copilot (reachable only on localhost 127.0.0.1)
cd deploy/A2-copilot/copilot
python3 text-cli-copilot.py

# Deploy A3 platform management service
cd deploy/A3-service/service
python3 main.py

# Deploy A5 integration endpoint gateway
cd deploy/A5-endpoint/python
pip install -r requirements.txt
uvicorn main:app --host 0.0.0.0 --port 29050

# Deploy A9 full capabilities
cd deploy/A9-advanced/service
python3 main.py
```

## Accumulation Relationship

A2→A9 accumulate and override tier by tier. A3 starts with A2 capabilities included; A9 is the full endpoint. Each tier's `deploy/` is the complete runtime up to that tier.

A0/A1/A5/BYPASS are pass-through synced — source is mirrored as-is and does not participate in the accumulation chain.

## Sync Mechanism

**`deploy/` is not hand-edited.** All files are generated from `src/skeleton/` by the build scripts.

```bash
# Skeleton source → deploy/ artifacts (all tiers)
python scripts/build-all.py

# Sync a single tier
python scripts/build-all.py A5

# Verify deploy/ consistency with source (for CI)
python scripts/build-all.py --check

# Assemble container build context (run build-all.py first)
python scripts/release/container/build.py              # only generate .build/ context
python scripts/release/container/build.py --build      # generate context + docker build
```

When `deploy/` content does not match expectations, run `--check` for diagnostics first, then run `build-all.py` to rebuild.
