## 现代AI的Agent的主要内容

### 1.1 先划界：本文讨论什么，不讨论什么

"现代 Agent"很容易被当成一个模糊的大词。展开之前，先划掉一项**默认基建**——**自带推理**。

不是它不重要，而是它不是 Agent 工程要解决的问题：推理是 LLM 本体的能力，对 Agent 工程而言推理**外部化**是常态——接入一个模型即获得，不存在"自己实现推理"这回事。真正的问题不是"有没有推理"，而是"推理怎么被调度"。

划掉它之后，剩下的才是 Agent 工程要一砖一瓦搭起来的能力层。

### 1.2 心智模型：一切能力都挂在 agent loop 上

现代 Agent 的行为可以用一条循环概括：

```
plan（规划） → act（执行） → observe（观察） → re-plan（再规划） → …
```

这条循环上有四个角色：

| 角色 | 干什么 | 通常由谁承担 |
|---|---|---|
| 决策者 | 决定下一步做什么 | LLM（外部） |
| 执行者 | 真正动手 | 工具 / 运行时 |
| 观察者 | 把结果转成可判定的信号 | 运行时返回信封 |
| 再决策者 | 读信号，决定继续 / 重试 / 换路 / 收工 | LLM（外部） |

**后面列出的每一项能力，都能在这条循环上找到自己的位置。** 判断一个系统"像不像现代 Agent"，就是看这条循环是否完整、每一项能力是否有明确的承担者。

### 1.3 能力清单

按循环角色分四组，共十一项：

**感知层——循环的输入口**

1. **感知与上下文管理**：接收多模态输入（文本 / 图片 / 音视频 / 文件）；管理长上下文（切分、召回、压缩）。
2. **状态感知**：感知当前环境状态（文件、进程、运行中的服务）并随操作实时更新。
3. **记忆**：短期工作记忆（当前任务的中间状态）+ 长期记忆（跨会话的知识沉淀，如用户偏好、项目约定、历史决策）；有写入、检索、遗忘机制。

**决策层——循环的大脑**

4. **推理**（外部化）：接入 LLM 获得理解、生成、判断能力。Agent 工程关心的是推理的**入口与出口**——输入什么上下文、输出什么动作。
5. **任务分解**：把大目标拆成可执行的子步骤，明确顺序、依赖与产出。

**行动层——循环的手**

6. **工具调用**：工具的注册与发现、参数校验、结果解析——是 Agent 接触真实世界的唯一通道。
7. **临时编排权**：Agent 不只是"选一个工具"，还要能**临场组织多步执行**——把若干工具串成一条执行计划（含数据流、分支、降级），交给运行时一次执行。这是 Agent 与"单函数调用"的分水岭。

**治理层——循环的刹车与仪表**

8. **自我评估与纠错**：把执行结果转成"是否达成目标"的可判定信号，驱动下一轮——继续、重试、换参数、换路、宣告完成。
9. **人机交互与人闸**：关键 / 危险操作前请求人工确认，分级授权，用户可随时打断、修正方向。
10. **安全治理**：凭据隔离、沙箱、敏感操作防护、熔断——越权行为在发生前被拦截。
11. **可观测性**：日志、调用链、成本计量——出了问题能查，跑得好不好能量化。

一句话收束：**现代 Agent = 感知接得住 + 决策想得清 + 行动做得到 + 治理刹得住。**

### 1.4 能力坐标系

把上述十一项压成八根主干坐标（推理已划界，见 §1.1；任务分解并入临时编排权；状态感知并入感知与上下文管理），每根给出**判定标准**（怎么算"有"）。这张表是全文的锚——第二章的轻量化示例将逐格对照它打勾。

| # | 能力 | 定义（解决什么问题） | 判定标准（如何算"有"） |
|---|---|---|---|
| 1 | 感知与上下文管理 | 接住世界的信息 | 支持多模态输入；能维护上下文并持续跟踪环境状态 |
| 2 | 记忆 | 记住"我是谁、做过什么" | 有长期记忆，且有写入 / 检索 / 遗忘机制 |
| 3 | 工具调用 | 接触真实世界 | 工具可注册、可发现、参数可校验、结果可解析 |
| 4 | 临时编排权 | 临场组织多步执行 | Agent 能生成多步执行计划，运行时一次执行、一次回包 |
| 5 | 自我评估与纠错 | 知道"目标达成没有" | 执行结果有标准化信号；Agent 据此自驱下一轮 |
| 6 | 人机交互与人闸 | 危险动作有人把关 | 有分级审批；关键操作可被打断 |
| 7 | 安全治理 | 越权在发生前被拦 | 凭据隔离、沙箱、敏感操作防护、熔断 |
| 8 | 可观测性 | 出了问题能查 | 有日志、调用链、成本计量 |

> 判定标准刻意写得"可对照、可打勾"。第二张能力账本会给每格打上三种标记：**✅ agent 内实现** / **⚡ 由 LLM 或 tc 运行时承担** / **❌ 暂缺**。

## 轻量化的示例 -tc-web-chat

现在用第一章的坐标系，看一个真实的最小实现：`tc-web-chat`。它要证明一件事——**标准很重，实现可以很轻**。

### 2.1 它是什么

tc-web-chat 是一个**完整的 Agent**，且只需一个 HTML 文件承载：

- **零安装**：没有安装包、没有登录、没有外部依赖库——双击 `tc-web-chat.html` 即开，打开即对话
- **不绑定平台**：把后端地址填进去，它就去问那个后端；回复里的资源直接内联渲染，不跳走
- **两套地址解耦**：聊天走 `Base URL`，指令执行走独立的 `tc_endpoint`——聊到哪、执行到哪，互不牵制

作为一个完整的 Agent，它的三个模块各司其职：

| agent 内模块 | 承担 |
|---|---|
| LLM（Base URL） | 推理 / 决策 |
| tc-web-chat | 协调 / 界面 / 人闸 |
| tc 运行时（tc_endpoint） | 工具执行 |

### 2.2 工具调用如何发生

启用 tc 后，一次提问按免打扰轮流动：

```
你的输入
  │
  ▼
[LLM 思考] → 直接回答 | 决定调工具
                    │
                    ▼
           前端代理发射 → tc 运行时执行 →（人闸卡）→ 结果回填 LLM
                    │
                    ▼
              你看到的最终回答
```

三个关键约定让"发射 → 执行 → 回填"可靠运转：

- **协议**：统一指令语法 `AI:domain;action,params`
- **信封**：响应固定为 `rst_types / rst_data / rst_err`——前端**只读 `rst_err` 判成功**（`rst_err === ''` 即成功），绝不靠 HTTP 状态码
- **错误码**：6 码闭集（`ERR_NOT_FOUND` / `ERR_EXECUTION` / `ERR_ROUTING` / `INVALID_PARAMS` / `ACCESS_DENIED` / `SERVICE_DENIED`），前端据此给出可操作的提示

### 2.3 临时编排权

LLM 不只是"选一个工具"——它能临场写一段**可执行程序**（多步 + 数据流 + 依赖声明），一次发射，运行时一次执行、一个信封回包。这就是第一章坐标系第 4 格：

```
AI:text-cli;path,{
  "id": "tomorrow-weather",
  "type": "pipeline",
  "version": "1.0.0",
  "input_schema": {"type": "object", "properties": {"city": {"type": "string"}}},
  "requires": ["map;geocode", "weather;query"],
  "steps": [
    {"id": "geo", "instruction": "map;geocode,{input.city}", "output_as": "geo"},
    {"id": "wx",  "instruction": "weather;query,{geo.city},tomorrow", "output_as": "wx"}
  ]
},{"city":"北京"}
→ text-cli 一次执行两步 → 一个信封回包 → LLM 组织成最终回答
```

- **编排权在 LLM**：步骤顺序、数据流（`{geo.city}` 跨步插值）、依赖声明，全部在发射时由 LLM 决定
- **执行权在运行时**：text-cli 负责按计划执行、降级、聚合——LLM 不碰执行细节
- 这正是 Agent 与"单函数调用"的分水岭

### 2.4 结果自驱

信封就是"是否达成目标"的判定信号：

| 信号 | 含义 |
|---|---|
| `status: ok / stop` | 业务层达成与否 |
| `rst_err: "" / 错误码` | 协议层成功与否 |
| `result` | 达成到什么程度 |

LLM 读信封自行决定下一步：继续 / 重试 / 换参数 / 换路 / 宣告完成。

到这里，第一章的 agent loop 四角色全部找到承担者：

```
plan（LLM 生成 path） → execute（tc 运行时） → observe（信封信号） → re-plan（LLM 自驱下一轮） → …
```

这条闭环就是 tc-web-chat 作为完整 Agent 的行为——决策交给它的 LLM 模块，执行交给它的 tc 运行时模块，观察与再决策发生在信封与 LLM 之间。

### 2.5 人闸与安全

治理层由 tc-web-chat 自身实现，三个机制保证"危险动作有人把关"：

- **三档人闸**：Read-only auto（默认，只读自动、有副作用弹卡）/ None（全部弹卡）/ Auto all（全部自动，危险档）
- **字节同一性**：弹给人确认的和运行时执行的，是同一份字节
- **熔断**：同一指令连续失败 3 次，自动转强制人工审

凭据安全：双令牌（`Authorization: Bearer <access_token>` + `Service-token: <service_token>`），凭据由运行时侧 `context.env` 注入——**前端不存储任何凭据**；资源渲染做 `http/https` 校验与 iframe `sandbox`。

### 2.6 能力账本

对照第一章坐标系逐格打勾：

| # | 能力 | 判定 | 承担者 |
|---|---|---|---|
| 1 | 感知与上下文管理 | ✅ / ⚡ | 多模态上传、对话历史（tc-web-chat）；环境状态由 tc 运行时承载 |
| 2 | 记忆 | ❌ 暂缺 | — |
| 3 | 工具调用 | ⚡ | tc 运行时执行（自有协议 + 信封） |
| 4 | 临时编排权 | ⚡ | LLM 生成 inline path，运行时一次执行 |
| 5 | 自我评估与纠错 | ⚡ | LLM 读信封判达成，自驱下一轮 |
| 6 | 人机交互与人闸 | ✅ agent 内 | 三档人闸 + 熔断 |
| 7 | 安全治理 | ✅ agent 内 | 双令牌 / 字节同一性 / sandbox |
| 8 | 可观测性 | ⚡ 最小形态 | 会话级 JSONL 导出留档（tc-web-chat） |

### 2.7 取舍落点

八格命中七格，缺的整格只剩记忆。**轻量化不是缺能力**——能力由 agent 内部模块分工承担：LLM 管决策、tc 运行时管执行、tc-web-chat 管交互与把关。缺的记忆格是 tc-web-chat 当前的选择，轻量是同一选择的结果而非代价——它的全能力由此也只需要一个 90 KB 上下的单文件。

### 2.8 可加减的骨架：从制品到源

tc-web-chat 不只是"一个 90 KB 的制品"——它是一个**模块化的骨架**：

```
tc-web-chat-src/          # 源（进版本库；丢 html 可重建，丢它才真丢）
├── shell.html            # 外壳真源（DOM + CSS）
├── tc-*.js               # 功能模块：config / cache / parser / approval / quiet / chat / integrate
├── i18n.json             # 唯一多语言源
└── build.js              # 零依赖拼接脚本 → 生成单文件制品
```

**能力加减发生在源层面**：加一个功能 = 加 / 改一个模块，重建即得新制品——不是在一大坨 HTML 里改。**语言偏好**只是定制的一个例子：`i18n.json` 加一行、`--lang` 重构建，就得到你的语言版单文件。

这**回扣了 2.7**：缺的不是"无法拥有"，而是"选择"——源是骨架，需要记忆，加一个模块；需要日志，加一个模块。**轻的不只是成品，轻的是改动的代价。** 使用者完全可以基于这个可用的骨架，按自己的功能需要，定制出自己的单页面 agent。
