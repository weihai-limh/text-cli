# 基于text-cli的渐进式AGI解决方案示例

## 能够解决哪些问题

### 流程：
```
问题 -> 问题分形 -> 查询策略 -> LLM基于'策略'生成 指令序列 -> text-cli 运行时 执行指令序列 -> 响应基于问题的'指令序列'最终结果
```

### 基础的开源解决方案：

这一节给出 text-cli 家族"基础的开源解决方案"的最小可运行样板，其核心是一个名为 **synth-loop** 的开源项目——以 LLM 网关形态暴露的"任务处理中枢"：对外兼容 OpenAI / Anthropic 端点，对内对每次请求做分类、路由、上下文拼装与多步推理，最终收束到唯一推理落点。

在具体的任务处理中 synth-loop 向三个方向分派：**strata-match** 供策略与工具及资源（决定"怎么想"）、**下游 LLM API** 供推理（决定"想得多好"）、**text-cli** 是指令执行引擎（决定"做得成什么"）——你写下的 `域;动作,参数` 正是在这里被真正执行、以三字段信封回包。换言之 text-cli 处在链路"执行末端"，是能力真正落地的那一层，其余组件只负责把意图组织成它认得的指令序列。

[**synth-loop**](https://github.com/weihai-limh/synth-loop)

[**strata-match**](https://github.com/weihai-limh/strata-match)

```
┌──────────────┐     OpenAI/Anthropic      ┌──────────────────┐
│  任何 Agent  │ ──────────────────────→   │   synth-loop     │
│  (客户端)    │                           │   localhost:13155 │
└──────────────┘                           └────────┬─────────┘
                                                    │
                          ┌─────────────────────────┼─────────────────────┐
                          ▼                         ▼                     ▼
              ┌────────────────────┐    ┌────────────────────┐  ┌──────────────────┐
              │   strata-match     │    │   下游 LLM API     │  │    text-cli       │
              │   localhost:13156  │    │  OpenAI/Anthropic  │  │  指令执行引擎     │
              │ 策略 + Prompt +tool │    │                    │  │                   │
              └────────────────────┘    └────────────────────┘  └──────────────────┘
```

**一句话立起三件套。** 给读者一个锚——**synth-loop 是大脑**（组织整个任务）、**strata-match 是顾问**（决定"怎么想"，供给策略与工具）、**text-cli 是手脚**（把意图真正做成）。一句话：strata-match 教它怎么想，synth-loop 组织它怎么做，text-cli 替它把事做成。

**最小例子：一次指令的完整往返。** 看一个最小、无需安装即可懂的请求，建立"说即触发"的直观：

```text
读者问：2+3*4 等于几？
synth-loop 分类 → 落到执行 → LLM 生成一句指令 → AI:tc-math;eval,2+3*4
text-cli 执行 →        {"status":"ok","result":14}
LLM 拿这个结果回答  →  "等于 14。"
```

这一次只调一个工具、一次一个信封。读者一句话进去，得到的是 text-cli 回包的信封，再由 LLM 组织成回答——这就是"说即触发"。

**跨工具例子：一个问题的多步处理。** 看一个需要跨多个工具的任务——查北京明天的天气：

```text
读者问：北京明天天气怎么样？

LLM 生成一段 path →  AI:text-cli;path,{
  "id": "tomorrow-weather",
  "type": "pipeline",
  "version": "1.0.0",
  "input_schema": {"type": "object", "properties": {"city": {"type": "string"}}},
  "requires": ["map;geocode", "weather;query"],
  "steps": [
    {"id": "geo", "instruction": "map;geocode,{input.city}", "output_as": "geo"},
    {"id": "wx",  "instruction": "weather;query,{geo.city},tomorrow", "output_as": "wx"}
  ]
},{"city":"北京"}

text-cli 一次执行两步 → 一个信封回包 → LLM 组织成最终回答
```

第一步 `map;geocode` 把"北京"定位成坐标存入 `{geo.city}`，第二步 `weather;query` 用它查天气。多步被收敛回一句 `text-cli;path`、一个信封——这就是跨工具编排的落地形态。

**链式相位示例（对应中等复杂任务）：根分形、子直出 path。** 中等复杂任务（如"整理一份出差报告"），根被分形出几个相位，每个相位直接落到 path 执行——**不再深层下钻**。链式的流程重点在"相位内部的闸门"：

```text
根分形 → [相位1] → [相位2] → [相位3] → 完成
            │            │
        (执行·固化)  (执行·固化)
            │            │
          [闸]        [闸]
```

闸不是"相位之间的一道门"，而是**每个相位内部的受控推进点**——它决定"这一个相位执行得成不成、够不够格固化推进"。同一个相位在执行中会依次过几个闸：

- **执行前的 path 确认闸**（可选）：LLM 生成的执行方案，先等确认再动手，防未过审就执行；
- **执行后的质量闸**：执行完，靠**闭集信封机械判定**成败——成功与否不靠 LLM 自己判断，而是比对信封里的状态字段，**状态可知不是"聪明"，是"机械可读"**；
- **人的审批闸**（高风险相位）：结果交给人批准，人可放行、可驳回重试、可中止整棵树。

任何一道闸不过，就**只回退重做当前这一个相位**（回到检查点），不废整条链。这就是链式的形态：**任务被切成几个顺序相位，每个相位在自己内部的闸上被可靠地放行或卡住，直接出 path 执行。**

**结构式相位示例（对应复杂任务）：LLM 自主分形。** 复杂任务（如"做一个跨周的活动筹办"），根分形后**是否够落地，由 LLM 自己判断**——若某个相位还不能直接解决，就继续细化成几个子相位；子相位还可能再细化：

```text
根分形
  ├─ 判够落地 → 出 path 执行
  └─ 判还需细化 → 下钻成子相位：
        ├─ 子相位A：造句柄
        ├─ 子相位B：安装句柄
        └─ 子相位C：使用句柄
            （每个子相位同样自决：够就落、不够再下钻）
```

结构式的核心是 **LLM 自主分形**——它一边推进，一边判断"这项能解决了吗？还是要细化成几个子相位分别做句柄、装句柄、用句柄"。于是任务长成一棵会随需要生长的树，能承接最复杂的任务。机械闸只在最后兜底（防失控）。

**收口：这个样板对应的，正是后面讲的"完备结构"的一部分。** 一句 `域;动作,参数` 进、一个信封出，是三件套共同跑通的最小样板；但完备结构不只这一条链路——它由两部分组成：**问题分形**（先看问题多复杂、决定走哪条路，前面两个例子就是它选到的"重路"）与**相位**（最复杂的任务，怎么长成一棵树、把难事做到底）。本节看到的是"一句话进、一信封出"的表象，后面 `为何声称渐进式 AGI` 会把这套结构讲透。

## 为何声称是'渐进式AGI解决方案'

### 主流认知：AGI 是什么

提到"AGI（通用人工智能）"，大多数人脑中的画面是：一个**像人一样什么都能做的单一模型**——写文章、写代码、做规划、指挥机器人，统统由它一个搞定。也因此，我们习惯把 AGI 想成一个**非此即彼的开关**：要么是 AGI，要么不是，没有中间态。

顺着这个画面，AGI 的命运几乎完全系在一件事上：**模型够不够强**。参数越多、训练数据越大，就越接近 AGI；不够强，就还差一口气。于是"追求 AGI"在许多人心中等价于"拼命造一个更聪明的模型"——仿佛只要把单点能力堆上去，AGI 就水到渠成。

### 主流认知的困境

但这条路的问题，比"追不上"更深——它可能**从一开始就追错了方向**。

主流叙事默认"模型越强，离 AGI 越近"。然而参数越大，模型的权重间被训练数据固化出的"稳定性张力"就越强：它越来越擅长在**既有认知及行为模式内**做局部最优——一个极其优秀的**保守策划者**，你给它一个模式，它能把它执行得尽善尽美。但恰恰因为这份模式被权重死死锁住，它几乎不可能自己突破——**被权重束缚的大模型，无法突破它被训练固化的"既有认知及行为模式"**。而 AGI 需要的，正是打破这套既有模式本身。**更大的参数，是更好的保守策划者，而不是能带来认知变革的东西；被权重锁死的既有模式，只能让 AGI 更远。**

所以真正的变革不在"参数"这一层（越堆越保守），而在"上下文"这一层。单点能力早已不是瓶颈——今天的大模型，单看一次对话、一次推理、一次工具调用，已经能出色完成大量智力任务。卡住我们的，从来不是"某个模型不够聪明"，而是**如何让一个已经足够聪明的模型，稳定地、可收敛地、可扩展地完成"任意"任务**。前者靠参数，后者靠的是：结构。而结构真正要做的，不是让模型变强，是让它在当下这一层发生三件事——

**第一层：用上下文的事实创造张力，克服保守。** 模型自己跳不出被权重锁死的既有认知，那就由外部结构把**当下的事实、任务的具体信息注入上下文**——这些事实落在权重之外，与模型固化的惯性模式之间产生**张力**。这份张力，就是在当下这一刻压过它保守倾向的力量。克服保守，不靠让模型变强，而靠用局部上下文里的新鲜事实，临时改写它权重里的惯性。

**第二层：在局部上下文空间里，放大参数的价值。** 一个被权重塑造的模型，只有被放进一个**局部、聚焦、重组过的上下文空间**（每个相位只看该看的那一块，不被全局污染），它那已经过线的单点能力才真正被用起来、对准当前任务。同样的参数，在精心组织的局部上下文里，产出远高于在混沌的全局里——**结构在局部空间中把参数的已有价值放大出来**。

**第三层：由此产出大于成本，成为能自我造血的现实能力。** 这三层合起来，让结构对"产出与成本"的关系从负和、零和翻成**正和**：不靠堆参数、不靠模型自我突破，而靠"注入事实制造张力 + 局部空间放大参数"这两步，让单位成本换回更多、更好的制品。只有这种产出大于成本、能自我造血的能力，才配成为 AGI 落地的基石——就像 LLM 的 code，正因为写代码这件事在扣除成本后仍有正收益，才从"演示"变成了"基础设施"。

### 方案的收束：AGI = 智能 + 完备结构

所以这套方案把 AGI 拆成两个正交的部分：

> **AGI = 智能（模型已经具备的认知能力）+ 完备结构（把它组织成"任意可实现任务都能完成"的形态）**

- **智能**，回答"它聪不聪明"——这一点，今天的 LLM 已经过线；
- **完备结构**，回答"它能不能稳定地把一件长任务做完、做成、做到底"——这一点，正是 text-cli 家族在做的事。

#### 基于text-cli的相位机制

完备结构的第一半，是"相位"——它回答"最复杂的任务，怎么在组织上把它做到底"。它的可见形态，是一棵**按任务当场生长、每层由 LLM 自决、机械兜底**的树：

```text
一句话进来
   │
   ▼
  LLM 规划：先把整个问题「分相位」——拆成串在一起、依次推进的一段段
   │   （这一段段，就是这棵树的「第一层」）
   ▼
 第一个相位
   │  「LLM 自决」：基于当下上下文、sm 查到的工具/契约，自己判断
   │     —— 这项够落地吗？还是要继续下钻？机械闸只在最后兜底
   ├─ 判够落地 ────────→ 落地为「叶子」→ 交给 text-cli 执行
   │                        一句 域;动作,参数 进、一个信封出
   └─ 判还需下钻 → 保持为「节点」→ 递归下钻子相位，再逐层自决……
        │                          （每个子相位重复同样的自决）
        ▼
   最深的叶子 → text-cli 执行 → 信封回包 → 质量闸判定
   │
   ├─ 通过 → 固化产物、更新认知，继续下一叶
   ├─ 失败 → 只回退到当前检查点，重跑这一支，不废整树
   └─ 结果大量"委托/部分完成" → 反向信号 → 重估为「节点」再分形
   ▼
一个结果出去
```

这个结构的关键，是每一步都由 **LLM 在当下重组过的局部上下文里自决**，而不是被预先编排：

- **「自决」**：每层该"继续分形"还是"落地执行"，由 **LLM 自己判断**——它基于当下相位上下文、sm 查询注入的能力与契约，决定这项够不够落地、要不要继续下钻。任务一变，LLM 的判断让树自然长成不同的形状。机械闭集校验只做**最后的兜底**：LLM 判完用它封住错误、触顶强制落地、契约缺失兜底，防止分形失控——**决策是 LLM 的，机械负责兜底**。
- **「递归」**：节点可以一层层下钻到任意深度，直到落到真正可执行的叶子；深度由 LLM 对任务复杂度的判断决定，不是写死几步。
- **「反向信号」**：如果一片"叶子"执行后暴露出它其实还不能落地（大量委托/部分完成），就把它**重估为节点**再分形——认可 LLM 第一次判可能错，判错可纠正。
- **「局部回退」**：某一片叶子错了，只回退到检查点重跑这一支，错误被相位边界截断，不废整树。

这就是"完备结构"：**它不靠模型变强，靠的是把一次推理组织成一棵可自决生长、可递归、可反向重估、可局部回退的树。** 相位化负责"这棵树怎么长"，text-cli 负责"每片叶子怎么落地"，二者合起来，让已经聪明的模型**接得住任意任务、跑得稳、可回退**。

于是有了一个关键区分：**"是否 AGI"由结构决定，"多好用"由参数决定，二者正交**。参数决定了同一个 AGI 完成任务的快慢好坏，但资格本身，由结构给。


#### 基于text-cli的问题分形及任务链

完备结构不只有"相位"这一半。在进入相位之前，还有一道**问题分形**——它先看这个问题有多复杂，再决定走哪条路。这是完备结构的另一半，也是绝大部分请求真正走的路径。（相位本身在上一节，这一节不碰它。）

**复杂度分类：先问"这问题有多复杂"。** 这是问题分形的第一道闸。任何一句话进来，系统先对它做一次复杂度分类——判断它是随手一问、要查资料、要调工具、还是要跑长任务。复杂度不同，投入的资源天差地别：一句"你好"不该消耗一次长任务的全部编排。

**分形路由：按复杂度选路。** 复杂度分类的结果，决定了走哪条路。关键在于——问题分形连"直答"也算一条路：

- **普通对话 → 直答**：最简单，直接由 LLM 回答，**不调任何工具、不走任何链**；
- **策略对话 → 注入策略 + 工具循环**：需要专家经验/工具时，注入对应策略，LLM 在一次次的工具循环里逐步推进；
- **任务链 → 拆链执行**：需要一次性处理多步时，把任务组织成一段执行链。

**并不是所有请求都会调工具或工具链。** 这是"问题分形完备"的关键：**LLM 基于任务判断是"直答"还是使用工具、创建异步任务链**。问题分形之所以"完备"，正因为它在最前面就把这些"轻请求"识别出来、用最轻的方式处理，把资源留给真正需要重处理的。会调工具/工具链的（策略对话、任务链），只是分形之后的一小部分。

**会调 text-cli 的那两条路，落到底都是 text-cli。** 两条"重"路对 text-cli 的组织方式不同，但底层都是同一套指令契约——只是调用方式不同：

- **策略对话 = 单调 text-cli 指令**：一次调一个——一句 `域;动作,参数` 进、一个信封出，结果回填上下文，LLM 再决定下一步。这是"单指令、多次迭代"；
- **任务链 = 合成一段 path**：LLM 先生成一段 text-cli 的 path（把多步指令串成一份可执行的编排），以这段 path 一次执行多步、一个信封回包。这是"多指令、一次编排"。

一句话：**策略对话一次一次地调 text-cli，任务链用一段 path 跑 text-cli；普通对话直答则不碰 text-cli。** 无论"单调"还是"path 多步"，都被 text-cli 统一收在"一句进、一信封出"之下。

下面用两个例子，把"单调"和"path 多步"落到能看见的实物上。

**单工具调用——策略对话里的"单调"：一次一个信封。**

```text
读者问：2+3*4 等于几？
LLM 生成一句指令 →   AI:tc-math;eval,2+3*4
text-cli 执行 →        {"status":"ok","result":14}
LLM 拿这个结果回答  →  "等于 14。"
```

这一次只调一个工具、一次一个信封。策略对话就是这样的"单调"——LLM 一步步来，每步生成一句 `域;动作,参数`、拿回一个信封、再决定下一步。

**path 多步——任务链里的"一次编排"：一段指令、一个信封。**

LLM 直接生成 path 指令时，把声明与输入数据作为两个独立参数，一句 `text-cli;path` 进、一个信封回包：

```text
AI:text-cli;path,{
  "id": "tomorrow-weather",
  "type": "pipeline",
  "version": "1.0.0",
  "input_schema": {"type": "object", "properties": {"city": {"type": "string"}}},
  "requires": ["map;geocode", "weather;query"],
  "steps": [
    {"id": "geo", "instruction": "map;geocode,{input.city}", "output_as": "geo"},
    {"id": "wx",  "instruction": "weather;query,{geo.city},tomorrow", "output_as": "wx"}
  ]
},{"city":"北京"}
→  text-cli 一次执行两步 → 一个信封回包 →  LLM 组织成最终回答
```

`{` 开头的参数被识别为内联 path 声明；逗号后的 `{"city":"北京"}` 是独立的输入数据。两步被串成一段 path，第一步 `map;geocode` 把"北京"定位成坐标存入 `{geo.city}`，第二步 `weather;query` 用 `{geo.city}` 查北京明天的天气。这就是"path 多步"——任务链把多步编排收敛回一句 `text-cli;path`，一次执行、一个信封。

**收口：问题分形 + 相位，合起来才是完备结构。** 问题分形（相位外）决定"走哪条路、轻还是重、要不要动 text-cli"；相位（相位内）决定"进了相位之后，任务怎么长成一棵树、怎么把最难的做到底"。二者缺一不可——**没有问题分形，所有请求都会挤进重处理，成本与复杂度一起失控；没有相位，最复杂的任务又没有一个能深做的兜底。** 于是全链路收拢成：**问题分形选路 → 轻的直答、重的或单调或 path 地调 text-cli → 一信封收束。**


### "渐进式"在哪：AGI 不是一个终点，是沿两轴生长

把 AGI 当成"智能 + 完备结构"，它就不再是一个静止的完成态，而是一个**沿两个方向持续生长**的过程：

- **广度轴（覆盖度 κ）**：结构能承接的任务越来越多。它靠两条路持续扩展：
  - **生产门槛极低**：一个能力包最小就是"一份 Markdown"（连代码都不用写）或"一个 schema + 一个 handler"。门槛低到"会说话就行"——生产者从"开发者"扩展到"任何会表达的人"（花店老板、盆栽爱好者）。能产能力的人变多了，覆盖度就有了持续的供给。
  - **小而完备，可与任何协议双向转化**：tc 的句柄是一个足够小、边界清晰的**最小契约**（一句 `域;动作,参数` + 一个三字段信封），所以理论上任何其他协议（MCP、function calling、自定义 schema…）都可以和它做双向转化——外部能力能桥接成 tc 句柄，tc 句柄也能转出去。这让广度轴不只靠人生产，还能靠**协议桥**把既有生态直接填充进来，覆盖度只增不减、单调上升。
- **高度轴（完成质量）**：同一个任务，在结构调度下被完成得越来越准、越来越好。

但高度轴**不是"模型越强、完成越好"**——那正是前面否定的主流叙事。这里需要先把 AGI 的两个维度分开看：**"突破范式"的维度**——能否跳出既有认知、创造新东西，在这个维度上大参数的保守是负的（被权重锁死，只能靠结构在上下文层突破，也就是前面说的"只能让 AGI 更远"）；**"落地执行"的维度**——能否把已知任务精确做对，在这个维度上大参数的保守恰恰是正的——**更保守，意味着对已知任务完成度更好，能更精准地对齐句柄、做出可执行的句柄**。这正是 AGI 落地最需要的那个"正刃"。

于是参数不是"天花板"，而是**结构手里的档位**：让不同的参数量各居其位——高参模型（保守但精准）负责规划、对齐句柄、复杂任务；小参模型（便宜够用）负责摘要、降级、轻量任务。**是结构决定用哪个参数量做哪件事，而不是参数自己决定 AGI 多高。**

所以两轴都由结构主导，而非互相独立：**广度轴靠结构扩展生态（造包、覆盖任务），高度轴靠结构调度参数（把每个档位放在它该在的地方）。** 两轴互相喂养、同时推进。这就是"渐进式"的本义：**AGI 不是"要么是、要么不是"的开关，而是一个沿广度与高度持续、不可逆地生长出来的过程。**

### 收口：为何"渐进"是必然，而不是妥协

也许你会问：为什么不直接宣称"这就是 AGI"，非要加一个"渐进式"？

首先，AGI 不可能一天建成的——它不可能某天睡醒突然出现。它只能靠把一个一个任务的制品价值，稳定地做到高于它的成本。

更深一层，"任意可实现任务"这个目标的结构本性决定了这一点：**永远会有下一个任务冒出来，任何有限的数据和训练都无法把这个"任意"封顶**。因此，"完成态"的 AGI 在逻辑上不可被证明到达——正因为没有一个"完成的瞬间"，也就不存在"某天睡醒突然 AGI"。

但"渐进"的必然性，不止在哲学，更在经济。**生长不是免费的**：造一个包要成本、维护生态要成本、跑每个相位每段 path 都要算力。只有当一个制品的价值**持续稳定地高于它的落地成本（正和）**，生长才是可持续的、不可逆的；反之——价值覆盖不了成本——生态会萎缩、覆盖度会下降，"生长不可逆"就崩了。所以"渐进"不是"我不够格所以慢慢来"，而是**"只有把制品价值稳定做高于成本，生长才可能持续"**——这是可持续生长的唯一形态。

而 基于text-cli的渐进式AGI解决方案，正是追求"价值 > 成本"能反复成立的那套机制：句柄生产门槛低、同维零税让消费便宜、path 把多步收敛成一次成本、结构在局部上下文里放大参数价值——**让"把制品做高于成本"这件事，变得可以每天重复、稳定发生**。

所以这句宣言是诚实的，也是进取的：**它不宣称"造出了 AGI"，宣称"AGI 是一个靠结构与句柄、把制品价值持续做高于成本、从而可持续累积的方向"。** 渐进不是退而求其次，而是"任意任务不可封顶"与"生长必须正和"这两个本性共同要求的形态。
