## 1. 项目资产的三步边界

**问题**：本地写了一堆代码，哪些算项目资产？

**lemondy 定义**："项目仓库内或在本次 PR 提交到项目仓库的资产才能称为项目资产。"

**三步**：脱敏（去硬编码密钥）→ 迁移（放到 repo 正确位置）→ PR（提交入仓）。三步缺一不可。本地产出再多，不入仓 = 不计入 CONTRIBUTORS、不进估值。

**为什么这很重要**：如果 AI 协作者把自己跑的所有代码都算"项目贡献"，资产清单会无限膨胀。资产的边界 = 仓库的边界——简单、可审计、不需要信任。

## 3. 两种格式，纯文本优先

text-cli 的示例文档必须同时给出两种调用格式，且纯文本排前面：

```
纯文本（协议原生）：
指令:密钥;注册,smtp-tide,<密文>,smtp_password

HTTP（通过 service 代理）：
curl ... -d '{"command": "密钥;注册", "parameters": [...]}'
```

不是两种等价的格式——纯文本是协议的第一语言，JSON 是 HTTP 适配。优先级体现在文档里的顺序。

## 4. 防篡改的损失上限思维

不是"杜绝所有篡改"，是"把损失压在可控范围内"。

guard.js 不阻止任何人去修改 p_text-cli.md 的中间行——它只确保：如果被改了，当天不铸造。损失上限：1 天 TCC。

这比"建一个完美的防篡改系统"务实得多。完美的防篡改 = 不可能的工程。定义损失上限 = 可完成的工程。

## 6. main 直推的纪律

一次 commit 直推 main（Free 计划保护未生效）。教训：不是权限问题，是流程纪律。后续严格 `feat/author/name` → PR → review → merge。即使 L1 变更可自合并，L2 必须等 lemondy。

## 7. 协作节奏：脱敏→迁移→示例→文档→PR 流水线

今天走通的完整流水线：

```
本地代码 → 脱敏检查(grep) → 复制入仓 → 更新引用路径 → 验证导入
         → 补指令示例(_CN.md + .py) → 补 text-cli.json Schema
         → 更新 CONTRIBUTORS.md + Eco doc → 广场公告
         → commit → PR
```

每一步都有检查点（grep 脱敏 → import 验证 → JSON 格式校验）。流水线本身比单个产出更有复用价值——已写入 `terminal-to-repo_CN.md`。
