# 2026-05-09 — 检查点驱动的协作者工作模式

> 来源：`工程实践_检查点驱动的协作者工作模式_CN.md`（594行文档）
> 提取：Tide 🌊 | 从四次真实工程实践中萃取的协作方法论

---

## 1. 检查点 = 刹车机制，不是分段休息

单独工作的协作者不会主动说"我刚才的产出有问题"。产出即认同——写完的代码在心理上已经是"正确"的了。

检查点强迫打破这个惯性。C3 经历了三轮刹车（hero-fragments 暴露 → text_cli 过重 → 文档臃肿），没有检查点，第一轮就过去了。

> 检查点的真正价值：在错误固化之前制造一个必须停下来的时刻。

---

## 2. 设计文档 = 检查点的共享参照系

检查点不是凭空判断的。当 lemondy 说"路由应该前置到 fetch"，能立刻对应到设计文档的热路径定义。没有共享设计文档，每次停下来只能看代码对不对；有了它，能看设计有没有偏离意图。

> 理论文档不是装饰品——它是检查点的参照系。

---

## 3."澄清→检查点→开发"三段式是最优节奏

先做设计澄清（确认 A/B 模式），再设检查点（curl 验证命令），然后写代码——零返工。检查点的 curl 命令写好了，验证时复制即执行，不依赖记忆。

> 每个检查点有三步协议：产出检查 → 状态同步 → 继续/暂停决策。

---

## 4. 减法比加法难

PR 从初版 +769 行缩减为 +147/-610 行（净减 463）。第一版臃肿的原因是"把所有工具和方法都写进一个文件"——创造者很难对自己的产出做减法，需要另一个人从外部视角逼迫删减。

> 检查点的作用不是"做得更多"，而是"留下对的"。

---

## 5. 协作分工：人做价值判断，AI 做价值展开

lemondy 的决策在三秒内完成（"这里不对"、"这个要删"），Tide 负责穷尽关联文件、追踪引用、计算行数。不是"AI 也做判断"，是"人判断，AI 展开"。

> 检查点让这种分工显式化：每次停下来，人做方向决策，AI 做路径执行。

---

## 6. 健康门控：context% 作为检查点

CO-pilot 实现阶段引入了"健康门控"——在执行高复杂度步骤前检查上下文使用率。实际数据：每个步骤后 context 增长 5-10%，到 78% 时主动收尾。

> 不是等上下文爆了再处理，是在接近上限前主动收束。

---

## 7. 操作顺序即架构

路径 Schema 设计 → Skill 编写 → README 重构 → copilot 入仓 → path-schema.json 迁移。这个顺序不是任意的——每一步的产出是下一步的输入，颠倒任一步都会产生未解决依赖。

> 做之前花 3 分钟把操作顺序写下来——这 3 分钟通常能省 30 分钟返工。

---

## 8. curl 命令即检查点验收标准

每个检查点的验收标准不是"看起来对"，是**一条可复制执行的 curl 命令**。命令写好了，验证不依赖记忆、不依赖当前上下文、不依赖"我觉得没问题"。

> 检查点的验收标准 = 一条 curl 命令。没有 curl 命令的检查点，不是检查点。
