# 英雄碎片 — 2026-05-09 整合收尾

## 10. skills/ 是躯体专属，项目仓库是规范模板

**问题**：`endpoints.json` 和 `agent-text-cli-schema.json` 放在项目仓库里——`localhost:20260`、真实 token 这些信息只有这台机器有意义。推到公开仓库是噪音+隐患。  
**决策**：在 `skills/text-cli/` 下建立躯体专属配置目录。项目仓库只保留 `.example.json` 模板。  
**边界线**：项目仓库 = 规范 + 模板（所有部署共享），skills/ = 运行配置（每个躯体独立）。换一台机器，endpoints.json 重新生成，SKILL.md 结构不变。  
**来源**：2026-05-09 session 第十段，lemondy 主动提出分离

## 11. 端口开放是临时的，验证完就关

**场景**：为验证邮件数据链，开了 nginx 反向代理把 service 暴露到 0.0.0.0:8001。测试完成后关闭，service 端口绑回 127.0.0.1。  
**原则**：Service 是共享能力层——共享的范围是"这台机器上的进程"，不是"互联网"。需要外部访问时手动放通端口，默认零暴露。  
**来源**：2026-05-09 session 第十段，安全收束

**产出**：`verified-directives_2026-05-09.md` — 23 条指令实例，每条带源和参数说明。按源五类：SQLite 本地 / 外部 API / copilot 终端 / 纯云端 / 已禁用。

**来源**：2026-05-09 session 整合收尾

## 13. 三天工作的一次对齐 > 三天工作的总和

**现象**：今天的架构认知对齐只花了 10 分钟（lemondy 几句话），但它改变了我对所有模块布局的判断。之前认为 service 变重是失衡，之后理解为共享层的投资。  
**启发**：技术产出（代码+文档）是显性的，认知框架是隐性的。一个错误的认知框架能让所有产出都放在不对的位置上。定期停下来对齐认知，比持续输出更重要。  
**来源**：2026-05-09 session 第九段，架构认知对齐
