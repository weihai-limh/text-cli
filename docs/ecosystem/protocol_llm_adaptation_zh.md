# text-cli 协议对 LLM 的适配

> **语言说明：** 本文为规范中文原文。其他语言译本若与本文冲突或存在歧义，均以本稿为准。

> 本文只回答一个更窄、也更硬的问题：text-cli 的协议，为什么对语言模型适配？中心化、版权、生态运营之类的问题属于上层治理，不在本文范围内。

## 0. 一句话纲领

协议把「最贵的一步（推理）」交给 LLM 最擅长的形式（一句受控的祈使模板），把「最便宜的一步（解析与归一）」甩给机器。schema 的严谨性没有消失，只是分了层：把**解析与归一的严谨性**挪到机器侧（parser/registry），而**输入校验的严谨性**留给服务方在其 handler 内。

凡是「要求 LLM 严格产出匹配 inputSchema 的 JSON 对象」的工具调用，做的是相反的事：它让 LLM 脱离「说人话」去生成一个结构严格、字段类型必须正确的 JSON，把序列化负担压在了推理侧。两条路的差异不是风格，是**阻抗失配由哪一侧吸收**的差异。

下文逐层展开这个分析。

---

## 1. LLM 在做什么：相关性 token 预测

要论证「对 LLM 的适配」，必须先老实说清 LLM 在干什么。一句话机制描述：

**LLM 的输出，是基于相关性的 token 预测，吐出有意义的文字连接。**

这不是翻译，也不是执行。LLM 不会「理解意图后切换到一个结构化模式去生成 JSON」；它始终在做同一件事——在给定上下文里，预测下一个最相关的 token，连成一段连贯、有意义、符合统计规律的文本。

这一机制事实直接决定协议为何成立：

- **指令是「生成文本」的子空间，不是「切换 mode」。** 当上层 LLM 在 text-cli 架构里做编排时，它只是在自己本来就运行的「受控文本预测」空间里，把 `AI:域;动作,参数` 这个祈使模板作为预测文本的一部分吐出来。祈使模板本就活在这个空间里（它是自然语言的一个最小受控子集），LLM 预测到它，不费事，也不需脱离「说人话」的模式。
- **适配是架构性的、普适的，不依赖最强模型。** 这个适配的来源是协议形状本身，不是某个旗舰模型的特殊能力。哪怕一个较小的模型，只要它能可靠地预测受控文本，就能用协议。这一点很重要：很多「对 LLM 适配」的设计其实只对最强模型成立，而本协议把靶心钉在了「能吐受控文本即可」这一档。

---

## 2. 协议原语：一个活在预测分布主轴里的受控模板

上一节说「指令是生成文本的子空间、不是切换 mode」；本节把这个论断落到具体的分布位置——祈使模板活在主轴的哪一截。

协议原语是：

```
AI:域;动作,参数
```

这是一个**祈使句的最小受控子集**。它不是自然语言的全集，但也不是另一套格式（比如二进制或某个 RPC 形状）。

对 LLM 而言，生成这一句落在它预测分布的**主干**上，不是边缘。对照「要求严格匹配 inputSchema 的 JSON 工具调用」：那种调用要求 LLM 在生成文本的同时，额外维持一个 JSON 结构——字段名精确、类型正确、必填项齐全、嵌套层级不错、引号括号不漏。这是一次**模式切换**，推理任务和序列化任务在同一个上下文里互相争夺注意力；序列化一旦错一个括号，整轮作废、token 重烧、重试。

而 `AI:math;eval,1+2*3` 不一样。这句话本来就是一句祈使，LLM 在「受控文本预测」空间里自然就会吐它，不需要「切换到结构化模式」。

需要澄清：这不是「自然语言」的全集自由，而是受控谱系上的一个**轻档**。把这一点讲清，是为了拆掉一个常见的假二分——见下一节。

---

## 3. 受控谱系：拆掉「JSON=受控 / 自然语言=自由」的假二分

讨论「受控模板 vs 自然语言」时，最容易滑进一个空二分：把 JSON Schema 当成「受控 / 严谨」一极，把自然语言当成「不受控 / 自由」另一极，然后说 text-cli 从自由降维到受控。这个二分是空的，必须拆掉。

**根本事实：没有不受控的谱系，自然语言本身也是受控表达。受控的表达才有语义。** 完全脱离所有约束的符号不是「自由」，是噪声——它不承载意义。符号的价值来自系统内的对立与差异，意义恰恰生于约束。

按这个框架，所有「能力调用格式」落在**同一条受控谱系**上，只是档位不同：

| 档位 | 约束来源 | 谁来执行约束 | 主要代价 |
|------|----------|--------------|----------|
| 自然语言 | 社会约定 / 统计规律 | 智能（人脑或 LLM 理解） | 歧义、需高智能解析 |
| text-cli 模板 | 显式轻语法 `AI:域;动作,参数` | 人和机器都能廉价解析 + 服务端归一兜底 | 弱类型强制 |
| 严格 JSON 工具调用 | 显式重形式（inputSchema） | 机器校验 | 冗长、占上下文、要求模式切换 |

三者**没有谁在谱系之外**。特别地，**严格 JSON 工具调用本身就是受控模板**——参数必须严格匹配固定结构、字段类型、必填项，它也是「按格式填的受控结构」，不是自由自然语言。所以 text-cli 模板与 JSON 工具调用不是「受控 vs 自由」的两极，而是**同谱系里的轻重两档**：一个轻、省 token；一个重、占上下文。

这条澄清废掉了两种错误叙述：

- 「text-cli 表达力弱于 JSON 工具调用」——错在把「约束强度」和「是否有表达力维度」混为一谈。text-cli 的参数体本身可承载结构化数据，协议靠**括号深度追踪**来处理参数内部的逗号，所以复杂参数不必被强制「拍平」，并非表达力天然更窄。
- 「text-cli 从自由自然语言降维到受控」——错。text-cli 不是在「自由」和「受控」之间选择，它是在**受控谱系内部**挑了一个「人和机器都便宜」的切点。

## 4. 供 LLM 消费的协议层端口

协议对 LLM 的适配，不只在「调用的形状」上（§2 的受控模板落到预测分布主轴），更在「模型怎么知道能调什么、怎么调对」上。text-cli 的指令包在协议层为 LLM 留了三类端口，使模型成为 schema 的**原生读者**而非**服从者**。三者合起来，把「发现能力、命中规范、读准期望」三件事直接开给模型——这正是「AI 原生」与「为机器 RPC 设计、再桥接给 AI」之间的分水岭（见 §4.4；根因见 §4.5）。

### 4.1 发现（query）：让模型读出「这里有什么」

标准运行时提供 `query,json`，返回当前已注册指令的**可枚举契约**（`directives[]` 及每项的 `domain` / `action` / `params`）。这意味着模型不必把任何指令名硬编码进权重或提示词：它可以在调用前**问**运行时「你能做什么」，再把答案纳入上下文去生成下一步。发现是协议层的原语，不是外部文档、也不是人工写死的知识——能力随包注册而**对模型可见**，随包卸载而消失。

### 4.2 别名归一：把约束的容错面放到入口层

机制：

- **规范名（domain / action）恒为 ASCII，是路由的唯一主键。**
- 一切非 ASCII 形式（中文、其他语言别名）由运行时经别名映射**归一化回规范名**后参与路由。
- 别名**双向、大小写不敏感**，但仅是规范名的访问入口，不改变路由主键。

举例（来自标准 weather 指令包的真实代码）：

```python
@directive("weather", "query", domain_alias="天气", action_aliases={"query": "查询"})
def query(params: list[str]) -> dict:
    ...
```

于是 `AI:weather;query,威海,明天`、`AI:天气;查询,威海,明天`、甚至拼错大小写、混搭中英文，服务端都能归一到 `weather;query` 后路由。约束仍在（路由主键是 ASCII 规范名），但**约束的容错面被放大到入口层**。

对 LLM 的意义：它**不必精确命中一个强类型 schema**，只需落到受控模板的宽容区间。它不需要去记住 `weather` 还是 `Weather`、用 `query` 还是 `查询`——任何有效别名都能命中。这恰好是 LLM 最舒服的位置：它只需近似命中，归一由机器兜底。

### 4.3 注册元数据：安装即声明「我期望什么」

指令包安装时即注册于运行时，声明其名字、别名与参数形状。这部分元数据是**模型可读的**：模型从 `query` 拿到的不只是「有个 weather」，还有「它要 `location` 和 `date`」。**期望的形状随包到达模型，而非埋在框架内部。** 这与传统做法相反——后者把契约锁在代码 / 框架侧，模型只能从训练记忆或人工提示里猜参数该长什么样。

### 4.4 与严格 JSON 工具调用的根本不同

把三类端口合看，差别不在「谁校验更强」，而在 **schema 的原生消费者到底是谁**：

- **严格 JSON 工具调用**的 `inputSchema` 本是为机器 RPC 设计的契约，AI 是**经桥接才到达**的。它的原生消费者是**校验器（机器）**——框架在边界拿 schema 做机器校验，LLM 只是被桥接进来的*生成方*：它生成 arguments，再由另一头的校验器决定收不收。模型不「原生消费」那个 schema，框架消费，再替它判生死。
- **text-cli** 反之把发现、别名、注册元数据三类端口**直接在协议层开给模型**，让模型读准而非被拒。模型是 schema 的**原生读者**：它问运行时有什么（§4.1）、用近自然语言的别名命中规范名（§4.2）、从注册元数据读到期望形状（§4.3）。

这正是全文脊梁的另一面：协议**在模型所在之处接住它**——不是逼模型过一道机器契约桥、再由校验器替它生死，而是把「调对所需的信息」作为协议层的端口直接供给模型。这与第 2、3、8 节同源：阻抗失配由机器侧吸收（§2 的解析归一、§3 的谱系切点），而「协助模型正确」的位置，被放在了模型这一侧能消费的地方。

### 4.5 调用平等：自然语言让调用平等

上文（§4.4）把「原生读者 vs 经桥接的服从者」的差别落在「schema 的原生消费者到底是谁」。这一节追到更深的来处：它不在工程选择，而在自然语言本身。

**什么是语言的平等。** 自然语言里没有对语义拥有终审权的仲裁者。两个说话者在「使用语言」这件事上是平等的 peer：意义从使用中产生，不从某一方的法令中产生；没有人被语言本身赋予「你说得不对、我不认」的特权地位。这不是社群的礼貌，而是语言作为 substrate 的属性——它生来平铺、无中心、任何能说话者皆可参与。也正因如此，语言里没有一道「谁有资格说话」的闸门：只要你在使用语言，你就在语言之中，与他人平起平坐。这份「自然」太寻常，反而常被忽视，但它是下面一切的起点。

**调用的平等。** text-cli 是活在语言里的文本协议，因此继承语言的形状：命名空间平、无仲裁者。于是它能把发现、别名、注册元数据三类端口直接开给模型，而不必先经一道机器校验桥再把模型当服从者接进来——因为模型与人在「使用语言」上是平等的 peer，协议无从、也无需区分「谁在说」。模型能成为 schema 的原生读者，不是协议赋予的特权，而是 LLM 的输出机制给了 LLM 能够平等使用协议的能力、协议只是把它落实成可操作的端口；字节层不区分人 / AI（§10 的调用同一性）正是这点的体现，不是设计偏好，是语言 substrate 在协议结构里的投影。

把上面的分水岭与 §4 的三类端口合看，协议其实把「一个能力存在」呈现为一个**可被确认的承诺**：安装即声明承诺，发现即确认承诺在场。于是三类端口正好对应这个承诺生命周期中模型能够消费的三个点：

- **§4.3 注册元数据 = 承诺可见**：安装即声明「我期望什么」，本质是运行时把一项能力承诺摊开给模型读；
- **§4.1 发现（query）= 承诺可确认**：模型问「这个承诺此刻还在吗」，协议实时确认其在场，而非给一份会过期的说明书；
- **§4.2 别名归一 = 承诺的容错入口**：模型不必精确命中规范名，任何近自然语言形式的别名都能落到承诺的主键上。

三类端口合起来，就是协议把「承诺—确认」这一截直接开给模型，让它在调用前就能读准、命中、确认一项能力——这正是 §4.4「原生读者 vs 经桥接的服从者」分水岭的底层原因：桥是给「不在语言里的消费者」准备的，而 LLM 一直在语言里，本就是承诺网络里的一个 peer。

**协议不施加中心化的指令语义约束。** 演进中的协议项目，其归一化机制尽量让别名的矢量空间在同等维度下接近规范名的矢量空间。

这种去中心化在 mesh 上有结构表现：接收指令的运行时同样能以完全相同的线格式将指令委托给另一个运行时。协议不区分"用户发出的指令"和"运行时转发的指令"——两者走同一条管道，收同一个信封。LLM 无需知道指令被转发了几次、经过了哪些运行时——对 LLM 来说始终是"一句进、封信出"。调用方只需向自己直接请托的 peer 出示 token，链上后续每一跳的凭证由各跳节点自行处理——指令的流转不由某个中心编排，而是由每一跳节点自身的路由声明决定。

## 5. 长度错误累积律：长链上 JSON 型调用的结构性劣势

这是全文最锋利、也最可验算的机制论点，其判断基于数学推演，不依赖任何「生态叙事」。

机制事实：自回归生成里，单个 token 出错率为 ε，整段 n 个 token 全对的概率约等于 `(1-ε)^n`，**整段出错的概率约等于 `1 - (1-ε)^n`**。错误率随长度**累积**。

每一个「严格 JSON 工具调用」是一个**独立致命点**：JSON 一旦 malformed，或某个字段不匹配 schema，整次调用失败、需要重试。串 N 个 JSON 工具调用去完成一件事，等于有了 **N 个独立致命生成点**。

关键在于：**强模型只把 ε 调小，调不掉那个 n 次方。** 这是结构性的，不是话术。算一下：

- ε = 1%（每 token 1% 出错），N = 30 次调用：失败概率约 `1 - 0.99³⁰ ≈ 26%`
- ε = 2%，N = 30：失败概率约 `1 - 0.98³⁰ ≈ 45%`

也就是说，即便是相当强的模型，串 30 个严格 JSON 调用也大概率在某一环翻车。而把模型翻倍变强，只是把 ε 砍半，n 次方还在——长链越是刚需，这个税收越是收不掉。

## 6. 路径编排：把 N 个致命点压成 1 个

text-cli 的路径（path）把「多步调用」声明为**一次生成**：一个 json 格式的 path 信封，内部是一串 step（宽容的指令序列）。路径非图灵完备，但支持条件判断（`if`）、单层循环（`mode:"map"`）与并行（`mode:"parallel"`），step 的 `mode` 字段取 `toolchain`（串行，默认）| `parallel`（并行）| `map`（循环迭代）三值之一。

机制后果：

- **致命点从 N 个压到 1 个**（path 信封本身），step 体是宽容的、可做兜底的。
- 对照第 5 节：JSON 型工具调用的长链是 N 个独立致命点；text-cli 的长链是 1 个致命点 + N 个宽容 step。

**诚实修正：是 N→1，不是 N→0。** path 信封本身是一段严格结构（含 `requires` / `steps[]` / `if` 对象），一个 30 步的 path 是一次**更长**的生成，它的单点风险高于一个短的 JSON 工具调用。所以准确的表述是「致命点 N→1，且 step 体可兜底」，不是「几乎不触发累计税收」。总失败概率从 `1-(1-ε)ⁿ`（N 个独立致命）变成「path 信封 malformed 的概率」（1 个致命）——仍远优于 N 个独立 JSON 调用，但非零。

**顺风论证：模型越强，text-cli 的优势越「不该缩小」，而非「越大」。** 数学上，严格 JSON 长链的失败概率约 `N·ε`，path 的失败概率约 `c·N·ε`（`c` 为 path 信封相对单 JSON 调用的平均长度倍数），二者都随 ε 线性下降、比值 ≈ `c`——即**相对优势基本恒定**，不随模型变强而「变大」。真正站得住的表述是：text-cli 在长链上恒定保持一个乘性优势，且 JSON 链的失败概率对现实模型强度（ε 不极小）始终顽固偏高，故协议「不因模型换代而过时」。唯一让绝对优势也随模型「变大」的合法前提是：模型变强使人们敢于编排更长的链（N 增大），此时绝对差值 `(c-1)·N·ε` 随 N 变宽——这恰好是协议「随模型升级而变强、而非被淘汰」的真实根源。

**迭代场景的进一步做实**：协议 `mode:"map"` 让变长迭代不再膨胀 path 信封——50 元素的循环成本从 O(N) 步声明降为 1 个 map step。N→1 的优势在迭代维度被拓宽：原来「串 N 个 JSON 调用」的累积税收，现在「串 N 个 step 的路径信封膨胀」也被收掉。须重申 §11 #1：map step 本身仍是 1 个致命点——是 N→1 的更强版本，不是 N→0。

## 7. 编排层的天然抗注入

机制：数据从一条指令返回后，只能落在**参数位**，逃不进**指令位**（数据逃不出指令位置）。

在路径编排里，这是真实存在的安全性质：step 的 `instruction` 字符串在**声明时固定**，插值只进参数位。于是 LLM 生成的编排文本里，来自上一步的数据难以被「翻转」成指令去污染后续步骤——污染被锁在参数位。

对 LLM 的心智减负是真实的：它不需要在每一步都提防「返回的数据里藏着一句能当指令使的恶意文本」。安全成本被挪进了接缝之后。

**边界必须补一句：** 这保护的是**编排层**，不保护**执行层**。插值后的参数若被 handler 拼进 shell 或 SQL，注入发生在 handler，协议管不到。协议诚实地把「编排隔离」和「执行隔离」分开——把两者混为一谈会让人误以为整体安全。

---

## 8. 一维契约与闭集错误信封

机制：入口一句祈使，出口一个结果信封 `{rst_types, rst_data, rst_err}`。聚合、路径、降级、联邦全部在接缝之后**不可见**。

对 LLM 而言，这意味着它只需要理解一个极简的因果：「**一句进、一个信封出**」。后端的真实形态——是单函数、是聚合、是跨网络降级、还是联邦 mesh——对调用方不可见。LLM 不必为「后端可能是一串复杂链路」付出上下文或推理成本。

闭集性质进一步强化这点：错误信封的形状是**有限、可预测**的（`rst_types` / `rst_data` / `rst_err` 三字段，业务错误统一走 `reason` 字段）。LLM 不需要面对一个开放的、千奇百怪的错误格式集合。它能稳定地预期「出了错会是什么样子」，而不是每次都要重新解析错误。

---

## 9. tracked 任务：最深处可以是一个真人

机制：tracked 任务在协议层把「远程能力」的终点开放给异步 / 人工。一个三天才回一次邮件的人，和一个 3ms 返回的函数，在协议层**没有区别**——都是「被一行文本触发、最终交回一个信封」。

对 LLM 的意义：它平时能调度的东西，默认被框在「代码 / 函数」里。这个设计把框拆了——编排可以跨越「代码边界」，延伸到字节之外的现实世界的服务。从协议视角看，human-in-the-loop 不是特例，只是另一个被一行文本触发、最终交回信封的端点。

（顺带说明：正因为原语层不区分「人发起」和「LLM 发起」，协议在线路层无法区分一条指令是被信任的人类授权的，还是 LLM 幻觉出来的。这是拓扑对称换来的真实代价，它如何被接住——协议给缝、上层完善、人闸把关——见第 10 节。）

## 10. 机制如何支撑一种人机协作模式：人审即所跑

§9 指出，原语层不区分「人发起」与「LLM 发起」，协议在线路层无法分辨一条指令来自被信任的人类还是 LLM 的幻觉。本文不把这一点当成协议的缺陷：它恰好让一种协作模式在结构上成立——人审即所跑；而问责由令牌关联这道缝（协议克制提供、上层完善）兜住。

一种自然的人机协作循环是：人用自然语言下指令 → LLM 准备 text-cli 指令或 path → **人审的是同一份字节** → 批准后执行。它的诚实性不来自「系统能分辨人和 AI」，而来自「人审的就是机器将跑的」。

**两层授权，分别在机制层和模式层接住代价：**

- **一次授权（令牌关联：协议给缝、上层完善）。** 向 AI 暴露一项能力（安装 / 注册，使其可被 `query` 发现）即是第一次授权：你授权该能力在本运行时的授权调用方下可被调用。但协议在此是克制的——它**不管理凭证生命周期**：密钥的分发、轮换、吊销是上层应用的事。协议只提供一道缝：令牌把一次调用关联到被授权的主体，标准运行时借此在调用侧做计量追踪；无代码的 nocode 文档型指令同样**接入这一关联**，而非自带一套凭证系统。密钥如何签发、何时轮换、令牌绑定到何种细粒度 scope，由上层通过**自定义运行时**完善：上层在这道缝上，把「关联」补全成完整的授权机制。
- **二次授权（协作模式层，人闸）。** 人在执行前审同一字节并批准，是第二次授权。它之所以可能，完全依赖上文的机制性质：受控谱系靠近自然语言（§3）使 text-cli 可读、一维契约（§8）使 path 可读、协议层为 LLM 留的消费端口（§4）使语义可达。人审的是字节本身，不是某份渲染摘要。

关键：**协议不靠「在字节里区分人 / AI」来化解危险（那做不到，也是设计使然），也不托底安全。** 它给的是令牌关联这道缝——上层在缝上把问责（调用侧计量 + 按调用人工批准）补全成单刃。一次授权在上层通过自定义运行时完善并兜底问责，二次授权在控制面兜底执行。

**对照严格 JSON 工具调用：** 那种循环里人批准的是系统渲染的摘要，执行的是另一份被重新物化的字节，二者之间存在漂移间隙（见 §3 对受控谱系的讨论）。text-cli 这一侧没有这道缝——批准对象与执行对象字节同一。

**效率不被闸门吃掉：** 人闸插在「准备」与「执行」之间，不增加 LLM 的生成次数。LLM 仍只生成一次 path，第 6 节的 N→1 税收保留，代价只是人类延迟——而风险操作本就该付这笔。

**1:N 授权不对称（map 引入的新风险）**：`mode:"map"` 出现后，人审的是模板（1 份字节），执行的是 N 次真实副作用（如对 50 用户各发一封邮件）。协议层保证不变：字节同一性——审的就是机器将跑的。但授权面从 1 扩到 N——审完一个模板不等于审完 N 个后果。控制面对 N 可见、可熔断，是上层服务的责任。协议的诚实在于不假装自己覆盖了这个授权差距。

本节是「机制使该协作模式得以成立」，不是「你应该用这种模式」。令牌关联作为协议的克制原语，其展开到此为止：它证明协议提供的是一道可被上层完善的缝，而非一个托底的凭证系统。人闸模式自身的边界（如审查是否真的发生）属上层应用工程，不在本协议机制边界之内。

## 11. 边界与常见误读

把上文分散的边界汇总到这里，并单列一类「常见误读」——把容易被误列为协议缺陷的错误观点原样摆出、逐条回应，以免读者把上层或通用的责任误归为协议属性。

### 第一部分：协议层的边界

1. **致命点 N→1，不是 N→0。** path 信封本身严格且可能很长，单点风险非零。
2. **抗注入在编排层，不在执行层。** handler 把参数拼进 shell/SQL 时，注入发生在 handler。
3. **反应式循环仍非声明式 path 的强项。** 协议通过 `mode:"map"` 对固定模板的变长集合迭代提供了一等支持——下笔税与长度税均被消解。但「每元素的下一步取决于本元素结果」的反应式循环（如逐元素跑工具、根据返回值决定下一个工具），仍不适合声明式 `steps[]` 的固定结构——这是形状差异，不是实现遗漏。
4. **校验在 handler 内，由服务方评价。** 协议层不做边界校验，params 原样透传；类型、必填、枚举、嵌套校验都交给服务方在其注册的 handler 内完成，是否充分由服务方评价，不是协议层的属性。这与 §4「模型是 schema 原生读者」同源：协议不把校验集中到自己的边界，而把完善留给服务方。trade-off：协议不替调用方在边界拦错，错误检测推迟到 handler；低风险调用划算，高风险调用需服务方在 handler 自补校验。

### 第二部分：常见误读（摆出错误观点并逐条回应）

以下三条常被误列为协议的「机制缺陷」。它们各自成立的条件、归属的层面不同；此处把错误观点原样摆出、再逐条回应，以免重蹈。

- **误读一：宽容语法让「能解析 ≠ 语义可靠」，故 text-cli 不可靠。**
  *错误观点：* 一句能解析的指令，不代表语义上是对的、安全的、符合调用方本意，所以协议不可靠。
  *回应：* 调用时就是按调用者的意图执行，与调用任何严格 JSON 工具没有分别——`AI:math;eval,1+2*3` 即你意图的那个计算，系统照做。意图本身对不对，是调用侧之事，是所有工具调用通用的，并非 text-cli 特有的机制缺陷。text-cli 真正特有的是「边界不做机器校验、校验交给 handler」（见 §11 第一部分 #4），那条已诚实列出；把调用者自己的意图问题扩成「语义不可靠」，是把通用责任误归为协议性质。

- **误读二：人审即所跑依赖人真读了，橡皮图章使闸门失效，故对称拓扑的危险暴露。**
  *错误观点：* 人闸不保证审查发生；若人未读即点批准（橡皮图章），第 9 节指出的危险重新暴露。
  *回应：* 审查是否真的发生，是上层应用工程（审查流程、操作文化），不是协议机制边界，也非本协议该负之责。协议提供「人审即所跑」的可读原语，使闸门在结构上诚实（批准对象 = 执行对象字节同一）；但「人是否真审」发生在部署侧，机制管不到，也不该由协议管。这与 §11 第一部分 #4 同理：责任由哪一层完成，协议不托底。

- **误读三：复杂 path 是文本墙，「可读字节 ≠ 人能通读理解每步」，故 text-cli 在复杂场景不可控。**
  *错误观点：* 30 步 path 可读性下降，人无法通读每步后果，协议因此不可读 / 不可控。
  *回应：* 路径如何渲染成可读的树、图或步骤列表，是上层集成应用的呈现责任，不是协议机制。协议只定义信封格式；「人审即所跑」的结构性质（批准 = 执行字节同一）不随呈现方式变化。其机制内核——长 path 信封 = 单点风险——已在第一部分 #1 覆盖。把「上层渲染没做好」说成「协议不可读」，是归属错误。

- **误读四：递归引用是安全漏洞，「协议允许无限递归，调用环不可控」。**
  *错误观点：* path/pro 的自引用递归（万物皆指令是递归结构）会形成调用环，协议未对此做任何限制，因此不安全。
  *回应：* 协议允许 path/pro 自引用是结构特性（指令以指令为原料），不设递归深度限制。检测真环（`A→…→A`）是运行时安全行为，不属于协议互操作边界——正如 SPEC 反复用 `>` 标"实现参考"、不把机制细节写入协议正文。各运行时宜在 `dispatch` 漏斗层按解析目标键闭合调用环，同时保留任意深合法递归；但这是运行时自身的防御工程，不是协议的强制性合规要求。

## 12. 收口

回到开头的问题：协议为何对 LLM 适配？十二节论证下来，答案可以收成一句话——

**协议把「贵且易错」的工作挪到便宜的一侧完成，且从不把能力锁死在某个时代的模型上限上。** 解析与归一带给机器（§2 的 parser/registry），「调对所需的信息」以模型能读的端口直接供给（§4），长链的累计税收压成一次生成（§6）。每一处适配，都是这同一句判断的实例。

这根判断的源头，在 LLM 自己的生成机制里（§1–§2）：LLM 始终在做相关性 token 预测，指令不是「切换到一个结构化模式」才生成的，它本就是「生成文本」的一个子空间；`AI:域;动作,参数` 这个祈使模板，正好活在这个子空间的主干上、而非边缘。所以「适配」不是协议给 LLM 加了什么能力，而是协议**没让 LLM 离开自己本来就在做的那件事**——它仍只是在预测下一个相关的 token。这是全文所有适配的根源。这根源还能再往下一层推：LLM 之所以能一直待在「生成文本」这件事里、并被当作平等调用方，是因为自然语言本身无仲裁、使用者在「使用语言」上平等——活在语言里的协议只能继承这形状，于是模型作为语言使用者天然坐在协议这张桌上（§4.5）。

把适配的来源拆成几根支柱，它们是上面那句话的具体形状：

1. **调用形状落在预测主轴，且拓扑对称（§2–§3）。** 祈使模板是「自然语言」的最小受控子集，人和 LLM 产出完全相同的字节、命中同一 dispatch，LLM 天然就是合法调用方、无需任何翻译层把它从自然语言桥接出去；协议在同一条受控谱系上（自然语言 / 轻模板 / 严格 JSON）挑了「人和机器都便宜」的档位——规范名 ASCII 做主键，别名把容错面放到入口层，LLM 只需近似命中。
2. **消费端口让模型做 schema 的原生读者，而非桥接服从者（§4）。** 这是与「要求严格匹配 inputSchema 的 JSON 工具调用」最根本的分野：后者的 `inputSchema` 本是为机器 RPC 设计的契约、AI 经桥接才到达，其原生消费者是校验器（机器），模型只是被桥接进来的生成方；text-cli 反之把发现、别名、注册元数据三类端口直接在协议层开给模型，让模型读准而非被拒。适配的第二根支柱，正在于「协助模型正确」的位置被放在了模型这一侧能消费的地方，而不是逼模型过一道机器契约桥、再由校验器替它判生死。
3. **长链税收从 N 压到 1，且优势恒定不随模型换代而消失（§5–§6）。** 串 N 个严格 JSON 调用等于 N 个独立致命生成点，错误率随长度累积、强模型也调不掉那个 n 次方；path 把致命点压成 1 个信封 + N 个宽容 step。更重要的是这是「顺风」：相对优势恒定保持（二者失败概率比值 ≈ 常数），且 JSON 链对现实模型强度始终顽固易错——故协议不因模型换代而过时。
4. **心智减负挪到接缝之后，并把编排延伸到字节外的现实世界（§7–§10）。** 编排层数据逃不出指令位（§7）、出口是闭集错误信封（§8），LLM 不必每步提防注入、也不必为后端复杂链路付出上下文；tracked 任务把能力终点开放给异步 / 人工（§9），人审即所跑的协作模式让对称拓扑的代价被人闸在控制面接住（§10）——其问责由令牌关联这道缝（协议克制提供、上层完善）兜住，而非由协议托底。

这一切能成立的前提，是协议保持克制：它只给「原语 + 信封」这道缝，不抢做凭证系统、发现目录或执行沙箱（这些由上层运行时完善，见 §10），也不把路径如何渲染成可读的树或图揽在自己身上（那是集成应用的事，见 §11）。「不因模型换代而过时」的结论已在支柱 3 给出，这里只补它的前提：小，是它故意的。

一句话：**协议假设机器应该去适配语言模型「预测文本」的实际行为方式，而不是反过来要求语言模型去适配机器的结构化约定。** 适应的方向反过来了，是协议适配 LLM 的全部根源。内核干净到几乎无法再减：一个 119 行的解析器，就是这个判断的物理体积。

## 附录: text-cli 公理 → 条款的显式推导链

> 附录只回答一个更窄、也更硬的问题：text-cli 协议的每一条强制条款，是从哪条公理机械地推出来的？边界、生态运营、实现参考之类的问题属于上层，不在本文范围内。

### 0. 一句话纲领

协议先立公理（关于"语言模型在干什么"与"自然语言是什么"的两个机制事实），再让每一条协议条款成为某条公理的必然推论。本文把"公理 X → 所以条款 Y 必须长这样"的推导步显式写出——不列结论，列推导。

凡是"协议为什么要求返回三字段信封""为什么入口宽松、校验推 handler 内"这类问题，答案都不在美学，而在公理的下游。下文逐条展开。

---

### 1. 两条公理（推导链在本文内的起点）

**公理 A（LLM 机制事实）：** LLM 的输出是基于相关性的 token 预测，始终在做"生成文本"这一件事；它不会"理解意图后切换到一个结构化模式去生成 JSON"。指令是"生成文本"的子空间，不是"切换 mode"。

**公理 B（自然语言机制事实）：** 自然语言本身无语义仲裁者，使用语言者在"使用语言"上平等；意义从使用中产生，不从某一方法令中产生。且自然语言并非"不受控"——它也是受控谱系上的一档，约束来自社会约定与统计规律。

A、B 自身不是设计选择，是机制事实；协议的全部条款都是这两条事实的下游。而 A、B 自身又是根公理 Ω 的下游投影（见附录 Ω）。

---

### 2. 公理 A → 调用形状条款

**推导：** 既然 LLM 始终在预测受控文本（公理 A），那么协议的调用原语必须活在这个预测分布的主干上、而非边缘——否则就是逼 LLM"切换 mode"，把序列化负担压回推理侧。

**所以条款 Y1（一维契约的调用形状）：** 协议原语定为 `AI:域;动作,参数`，它是自然语言祈使句的最小受控子集。LLM 生成它不费事，不需要脱离"说人话"。

**所以条款 Y2（规范名 ASCII、别名入口容错）：** 路由主键必须是机器能廉价解析的 ASCII（`domain;action`），但容错面必须放到入口层——非 ASCII 别名由运行时归一回规范名。这正好把 LLM 放在"近似命中即可"的位置（公理 A 下 LLM 最舒服的点），归一由机器兜底。

若违反 Y1/Y2（例如要求 LLM 输出严格匹配 inputSchema 的 JSON），则直接撞回公理 A 的反面——逼 LLM 切换 mode、序列化错误即整轮作废。故 Y1/Y2 是公理 A 的必然。

---

### 3. 公理 A → 校验位置条款

**推导：** 公理 A 说 LLM 吐的是文本、不保证结构严格。那么"输入校验的严谨性"若放在协议边界（像严格 JSON 调用那样在边界拿 schema 硬校验、错了打回），就等于把本该机器做的事又推回推理侧——与公理 A 的适配方向相反。

**所以条款 Y3（校验在 handler 内，边界不拦）：** 协议层不做边界校验，params 原样透传；类型、必填、枚举、嵌套校验都交给服务方在其注册的 handler 内完成。协议只把"解析与归一"的严谨性留在机器侧（parser/registry 把文本归到规范名），把"输入校验"的严谨性留给 handler。

这是阻抗失配由哪一侧吸收的差异：公理 A 要求把贵且易错的步（解析）给机器，把"LLM 只需吐宽松文本"的便宜留在推理侧。Y3 是这一判断的实例。

---

### 4. 公理 A + 长链数学 → 路径与信封条款

**推导：** 自回归生成里单 token 出错率 ε，n 个 token 全对概率 ≈ (1-ε)ⁿ，整段出错 ≈ 1-(1-ε)ⁿ。串 N 个独立 JSON 调用 = N 个独立致命点，强模型只把 ε 调小、调不掉 n 次方。公理 A 下 LLM 仍不免出错，故长链必须被"压缩成一次生成"。

**所以条款 Y4（路径声明式 + 致命点 N→1）：** 协议提供 path——一条声明式信封内部串 N 个宽容 step，LLM 只付一次推理成本，运行时确定性 `dispatch()` N 步。致命点从 N 压到 1 个 path 信封。

**所以条款 Y5（闭集错误信封）：** 出口必须是有限、可预测的形状 `{rst_types, rst_data, rst_err}`，业务错误统一走 `reason`。否则 LLM 每次都要重新解析千奇百怪的错误格式，违背公理 A 下"让模型少费神"的取向。

诚实修正（继承适配文档 §6）：是 N→1，不是 N→0。path 信封本身严格且可能很长，单点风险非零。但相对 N 个独立 JSON 致命点仍远优，且相对优势恒定不随模型换代消失。

---

### 5. 公理 B → 人机同平面与去中心化条款

**推导：** 公理 B 说自然语言无仲裁者、使用者平等。协议原语活在自然语言谱系里，就继承这形状：命名空间平、无中心、任何能说话者皆 peer。于是协议无从、也无需区分"谁在说"。

**所以条款 Y6（字节同一性：不区分人 / AI 发起）：** 协议在线路层不区分一条指令来自被信任的人类还是 LLM。人审即所跑——人审的是同一份字节，批准后执行的是同一份字节。

**所以条款 Y7（去中心化结构属性）：** 用户指令与运行时转发指令走同一条管道、收同一信封；协议不要求中心目录。运行时 `install` 一个包 = 把 `domain;action` 登记进本地语义表（"学会一个单词"），无中心词库下发。这是公理 B 在协议拓扑上的投影，不是运营选择。

**所以条款 Y8（发展不通过中心可见）：** 因 Y7，每个运行时自托管、语义表本地、发现目录可选，部署无需向任何中心登记。一个本地 nocode 服务不会出现在任何全局地图——"数不到节点"不等于"没有节点"。这是公理 B 去中心化形状的必然方法论后果。

---

### 6. 公理 B → 语义互操作条款（继承，非制造）

**推导：** 公理 B 说意义从使用中产生、无仲裁者。协议把原语钉在自然语言上，就自动继承了自然语言的语义平面——人和 AI 用同一门语言对话能续上，就是语义互操作存在的证据。

**所以条款 Y9（协议不施加中心化语义约束）：** 协议只统一调用语法、发现、回报、供给的坐标，不保证跨运行时语义一致。语义对不对是上层/服务方责任（handler 内评价）。协议"继承"语义互操作，而非"制造"它——故"破壁"应表述为"继承自然语言平面而自然消解"，不是"协议推倒了墙"。

### 8. 收口

回到开头：协议每一条强制条款，都能追到公理 A 或 B 的机械推导。

四根支柱（原语红利 / 消费端口 / 长链 N→1 / 人机同平面）不是并列的"特性"，而是同两条公理的不同下游。任何一条新条款，若不能挂回 A 或 B 的推导链，它就不该进入协议强制基线——只能作为参考实现的便利机制（演进只加便利，不改动底线，见 README「协议与项目的边界」）。

一句话：**协议的小，是推导出来的，不是裁出来的。** 每删掉一层，都能指回某条公理说"这一层违反适配方向"；每保留一层，也都能指回某条公理说"这一层是必然"。推导链闭合，协议才闭合成最小协议。


**根公理 Ω（语义空间同构）：** 问题域一旦用自然语言描述，就落在与 LLM 表征空间**同构**的语义空间里；建模 / 结构化不是必需，而是额外的"税"。因此适配方向必须反转——不是把问题规整成机器格式去喂 LLM，而是让机器反过来适应 LLM 已在其内的语义空间（README「最贵推理给 LLM、最便宜解析给机器」即此反转的落地）。

**为什么 Ω 是根、却放在附录：**

- Ω 是反常识断言。在读者尚未走完 A/B → Y1–Y9、尚未亲手确认"裁掉的每一层都能指回公理"之前，Ω 没有经验基底可依附，只会被当成狂妄口号——而这正是它不能被言说于开头的原因。
- 故本文刻意把 Ω 留到最后：先给出可由协议文本直接验证的下游投影 A、B，让读者在可证实的梯级上走到顶，再回头一看，全链都指向 Ω。Ω 从"主张"变成"收口"。

**Ω 如何收口 A、B：**

- **A 是 Ω 在"LLM 侧"的切片**：既然问题域已在 LLM 的语义空间里，LLM 始终在预测受控文本、不切换 mode，就是同构下的必然机制事实——于是原语必须活在预测主轴（Y1/Y2）、校验推 handler（Y3）、长链压缩成一次生成（Y4/Y5）。
- **B 是 Ω 在"自然语言侧"的切片**：既然语义空间由自然语言承载、无仲裁者，自然语言的使用者即天然 peer、分布即天然拓扑——于是字节同一性（Y6）、去中心化（Y7/Y8）、继承语义互操作（Y9）都是同构在协议拓扑上的投影。

**收口句：** A、B 不是并列起点，是 Ω 的两个正交切片；Y1–Y9 不是九条独立条款，是 Ω 经 A、B 两条切片在协议层的九处必然投影。本文正文从切片起推（可验证），附录回到根（可接收）——这正是"公理化 → 不被笑 → 可接收 → 可传授"在单篇文档内的阅读顺序实现。
