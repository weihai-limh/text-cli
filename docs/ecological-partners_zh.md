# text-cli 与生态参与者共同成长

> 基于 [协议规范](./SPEC_zh.md)。本文按参与者如何自然延伸的成长路径，组织生态参与者的收益，而非按角色目录罗列。
> 注：文中"消费者/生产者/私有运行时拥有者/指令集成服务商"为本文叙事术语，分别对应协议中的调用方/能力提供方/运行时拥有者/集成端点运营者。

---

## 1. 和 text-cli 共同成长

你第一次接触 text-cli，多半是想做点具体的事——调一个能力、跑一条指令。这条路通常从「先用起来」开始，而非从「选一个角色」开始。

text-cli 的参与路径因此是一条**涌现式成长链**：你从消费者起步，随着自己的需求和能力自然滑向下一站，每一站都由上一站的真实需要催生，没有人需要一上来就规划好身份。

```
消费者（调用者）
   │ 你手上有个能力想让别人也能用
   ▼
生产者（发布者）
   │ 你在意数据驻留 / 隐私 / 管控粒度
   ▼
私有运行时拥有者（管理者）
   │ 你想服务外部组织 / 变现 / 做跨组织枢纽
   ▼
指令集成服务商
```

> 典型路径，非必经顺序；同一主体可同时具备多站身份，也可在任何一站停下。

- **消费者（调用者）**：先用起来。拼一条 `AI:<域>;<动作>,<参数>` 就能调度技能，最低摩擦进场。
- **生产者（发布者）**：你有个能力（脚本 / MCP tool / 知识）想分享，又不想逐个对接用户 → 封装成可安装指令包。
- **私有运行时拥有者（管理者）**：作为生产者或重度使用者，你开始在意数据留在自己这边、凭据不外露、管控粒度更细 → 部署自己的运行时，「货架」归你管。
- **指令集成服务商**：你跑的运行时想服务外部组织、或想变现、或想做连接多组织的枢纽 → 部署指令集成端点，签发 Access Token、与上游私约结算。

**关键论调**：你**不必走完全程**——多数人停留在消费者身份就够用，也有人止步于发布者或私有运行时。后面的站不是「必须选」，而是「需求涌现时自然走到」。身份可叠加：同一主体可以既发布包、又跑端点。

↳ 从「私有运行时」迈向「连外部节点」的过程中，你会自然碰上跨节点编排需求——那一刻，**联邦 mesh** 的价值才真正显现（详见 §4 联邦 Mesh 注册表指引）。

## 2. 每站你得到什么

下述四站按成长顺序排列（仅文档叙述顺序）。每站先讲**你为何会走到这站**（涌现逻辑），再讲**随之而来的核心收益**——通用平台能力不再逐站重复，统一收在"共享价值底座"，更多机制细节见速查表。

### 2.1 消费者（调用者）

**你为何会走到这站**：你想用 AI 调度一些能力，但不想为每个工具重复编写调用胶水、不想在每一轮工具选择时反复消耗推理 token。这是整条链的入口，零门槛。

**核心收益（从「为何来」推导）**
- **一条指令调度所有后端**：`AI:<域>;<动作>,<参数>` 同时适用本地工具 / web API / 容器 / nocode / 跨节点 mesh 多跳，不用为不同后端写不同胶水。
- **不为「选工具」烧 token**：关键词/向量匹配减少工具选择环节对推理的依赖，响应单行结构化（rst_err 字段），显著降低工具选择对上下文的占用（相比逐工具加载完整 JSON Schema）。
- **一个入口收敛多提供方**：聚合入口（详见 SPEC §5 聚合与降级链）把多后端收成一个，单提供方失败自动切下一个，你只看到一个入口。

**如何起步**
```
拼指令：AI:<域>;<动作>,<参数> → POST /text-cli/cli
   → 解析 rst_err / rst_data
   → [多步] 路径编排；[多后端] 聚合入口
```

**注意**：你只传 Service Token 的值、不拥有其语义；不依赖公共示范端点（生产请指向可信 endpoint / 本机）；降级链背后的具体提供方对你透明，这是设计意图。

**调用检查清单**
- [ ] 指令用 `AI:` 前缀
- [ ] 处理 `rst_err`：NOT_FOUND 换路 / EXECUTION 重试 / ROUTING 停+告警（详见协议规范错误码章节）
- [ ] 长任务用 `GET /tasks/{id}` 轮询
- [ ] 生产环境指向可信 endpoint（或本机），不默认公共示范端点

---

### 2.2 生产者（发布者）

**你为何会走到这站**：作为消费者用顺手后，你手上有个能力（一段脚本、一个 MCP tool、一份知识）想让别人也能用，又不想为每个调用方逐个对接。封装成包，一次编写、处处可装。

**核心收益（从「为何来」推导）**
- **写一次，处处可装**：按协议规范的格式写一份 `schema.json`，即可被任意兼容运行时的 `text-cli;install` 直接消费；随运行时分发作为启动包，调用方「安装即验证」——你不必逐个对接用户。（"处处可装"指走标准 install 管线的运行时；CloudBase 为独立契约的旁路运行时、Copilot 为独立信任档位的本机代理，二者不在此列——见 [产品文档] 的「三道信任边界」章节与 [包发布指南] 的字段规范。）
- **已有工具零成本上架**：MCP 桥自动把 MCP tools 编译成指令，Skill 桥映射外部 skill，已有能力不需要手写转指令。
- **被生态自然触达**：你的包一旦被某指令集成端点收录（或被你自建端点托管），即可经该端点的聚合入口与 mesh 多跳、归一化路由被不直连你的调用方命中。（前提：目标调用方需能路由到一个已收录你包的端点——即通过该端点的 `/text-cli/skills`（SPEC §1.2.7）或 mesh peer 路由注册（SPEC §2.3）可见。项目不提供跨运营方的中心化包目录；跨陌生运营方的发现由运营方自建索引或社区发现层完成，项目仅提供可寻址能力原语。）
- **顺手变现（可选）**：若你想变现，可与指令集成服务商约定**结算价格**（私有账本）；Service Token 由你与调用方私约、端点只透传（详见 2.4）。

**如何起步**
```
写 schema.json（四种载体 native/nocode/aggregate/pipeline 按需选）
   → 本地 text-cli;install 自测
   → 提交发布 → 随运行时分发，调用方安装即验证
   → [可选] 与指令集成服务商约定结算价格变现（见 2.4）
```

**注意**：项目不保证你的包有调用量；商业结算须自行与指令集成服务商约定，项目不托管、不统一定价。

**发布检查清单**
- [ ] `schema.json` 符合协议规范（id/type/runtime/category/locales/trust 齐全）
- [ ] 本地 `text-cli;install` + 实际调用自测通过
- [ ] `directives[].outputs` 声明为字符串数组（影响 pipeline 引用）
- [ ] 如需商业变现：已与指令集成服务商约定结算价格；Service Token 与调用方私约
- [ ] `trust` 字段取值（internal/community/public）与事实一致

### 2.3 私有运行时拥有者（管理者）

**你为何会走到这站**：作为生产者或重度使用者，你开始在意数据留在自己这边、凭据不外露、管控粒度更细——不想把一切交给别人托管的端点。部署自己的运行时，「货架」归你管。

**核心收益（从「为何来」推导）**
- **账单成本可控**：dispatch 是纯 stdlib 关键词匹配而非 LLM 推理，你最在意的工具调度开销直接体现在账单上，不被「选工具」的推理成本悄悄吃掉。
- **数据留在自己这边**：可全本地部署（A2/A3），凭据走 `key_registry` 不外露（通过 `key;register` 指令注册，见 [用户手册] §3.4 密钥管理）；指令/路径层声明式抗注入，但 subprocess 执行面仍需白名单防护。
- **管控粒度自己定**：`service_manifest` 白名单最小暴露（配置格式见 [design_zh.md] §安全面 白名单管控）、前置配额、mesh 凭证、双层令牌分离——全在你能碰到的地方。
- **一键生命周期**：`text-cli;install / uninstall / export / packages` 管理包；`installed_packages.json` 追踪来源/类型/文件/时间；卸载自动清理 handler_inits + manifest + 删表。

**如何起步**
```
选形态 (A0–A9) → 部署运行时 (A2/A3/指令集成端点…) → text-cli;install 灌包
   → 配 service_manifest 白名单（见 [design_zh.md] §安全面 白名单管控）→ 开 /health 与监控
   → [如需对外] 参考 2.4 运营指令集成端点
```

**注意**：私有运行时拥有者默认只做内部运维、不自动具备商业结算身份；若对外商业化运营指令集成端点则同时是指令集成服务商（见 2.4），身份可叠加而非互斥。项目不替你托管运行时或兜底可用性；默认不对外运营公共示范端点（`test.text-cli.com` / `api.text-cli.com` 仅为非盈利示范）。

**运维检查清单**
- [ ] 运行时形态选择符合本单位需求（A0–A9）
- [ ] `service_manifest` 白名单按最小暴露原则配置
- [ ] 凭据经 `key_registry` 管理，未硬编码
- [ ] `/health` 与异步任务端点可观测
- [ ] 包来源经 `installed_packages.json` 可追溯
- [ ] （如对外运营）已读 2.4 完成计费/限流设计

### 2.4 指令集成服务商（连接/结算侧）

**你为何会走到这站**：你跑的私有运行时想服务外部组织、或想变现、或想做连接多组织的枢纽。这时你部署指令集成端点，把「内部货架」变成「对外的服务入口」。

**一句话定位**：你部署一个指令集成端点，对外签发 **Access Token** 给调用方；计费、限流、客户区分**全部在端点层私有实现**，项目不介入、不统一定价、不提供生态货币。你与上游技能提供方约定**价格/结算**（双方私约），而 Service Token 由**调用方与技能提供方**私约、你的端点只透传。

**计价底座：双层令牌（详见协议规范鉴权章节）**
```
调用方 ──Access Token──> 你的指令集成端点 ──透传 Service Token──> 技能服务
```
| 令牌 | 谁签发 | 作用 | 端点行为 |
|------|--------|------|----------|
| **Access Token** | **你（指令集成服务商）** | 验证调用者身份 | 端点校验其有效性（对应 `ACCESS_DENIED`） |
| **Service Token** | **调用方与技能提供方私下约定** | 端点**透传**给上游 | 端点只做 `extract_st_prefix(token[:8])`，不关心后段结构 |

关键约束：前缀不变性原则（端点只取前 8 位做策略控制面识别，身份码位数可扩展，端点无感知）；端点不拥有 Service Token 语义，它只是管道。

**盈利模型（指令集成服务商视角）**
你部署端点并向调用方签发 Access Token、约定资费；同时与上游技能提供方约定价格/结算方式（双方私约，项目不托管）。Service Token 由调用方与技能提供方自行约定，你只透传——端点只是管道：校验 Access Token → 透传调用方带来的 Service Token → 在 mesh / 多提供方时注入凭证 → 返回结果。

**如何运营（步骤）**
1. 部署指令集成端点（实现 HTTP API：`POST /text-cli/cli`，`Service-token` 头）；
2. 与上游技能提供方约定价格/结算方式（双方私约，项目不托管；**Service Token 由调用方与提供方自行约定，你只透传**）；
3. 向调用方签发 Access Token 并约定资费；
4. 端点管道：校验 Access Token → 透传调用方带来的 Service Token → 在 mesh 或多提供方时做凭证注入 → 返回结果；
5. 按私有账本分别向上游结算、向调用方收费，项目不提供跨参与者统一账本。

**配额 / 限流 / 降级（可选但推荐）**
| 能力 | 契约依据 | 指令集成服务商用法 |
|------|----------|-----------|
| 前置配额检查 | `quota;check,<target>[,<amount>]` | 调用前检查额度，耗尽返回 `{"status":"stop"}` 额度耗尽信号 |
| 多提供方降级 | 聚合指令 | 单提供方失败自动切下一个，调用方无感 |
| 错误码 | 协议定义的错误码（ERR_*） | `ACCESS_DENIED`/`SERVICE_DENIED` 映射计费/鉴权失败 |
| Mesh 多跳 | `peer_credentials` | 多节点联邦按 peer 注入凭证。分两级：(A) 基础 Mesh——纯路由转发，不提供凭证注入，属可用性优先形态；(B) 有凭证 Mesh——通过独立凭证注入器按 peer 注入凭证，凭证缺失时可配置拒绝或降级转发 + `_mesh_credential_degraded` 标注。高安全部署可启用 `mesh.require_credentials` 拒绝无凭证跨跳 |

> **安全提示（协议级）**：上表"无凭证转发"是为避免单点缺失导致整链失败而设计的**可用性优先**降级，**非安全推荐**。生产 mesh 应确保 peer 凭证持久化**可用**（具体持久化机制由运行时实现决定，协议不规定）；否则未授权节点可能收到本应带凭证限定的请求。Mesh 分基础（纯转发）与有凭证两级：基础形态不提供凭证注入，有凭证形态通过独立注入器按 peer 注入凭证，`require_credentials` 开关控制高安全部署是否拒绝无凭证跨跳。降级响应带 `_mesh_credential_degraded` 标注，供调用方程序化感知。

**计费方式建议（参考，非强制）**：按调用次数 / 按 Token 折算 / 包月阶梯。一切建立在私有约定之上，**不在端点间假设统一计价单位**。

**与公共示范端点的关系**：`test.text-cli.com` / `api.text-cli.com` 是项目非盈利示范/引导端点（见 `registry/endpoints.json` 的 `demo-public`），仅供体验与示例，**不参与商业结算**。你部署的指令集成端点是独立商业实体，与之无财务绑定。

**注意**：不定义生态统一货币或跨端点结算；项目不托管或担保任何端点的履约；不规定具体费率。

**上线检查清单**
- [ ] 端点实现协议 HTTP API（`/text-cli/cli`、`/text-cli/health`、`/text-cli/skills`）
- [ ] Access Token 签发与校验（映射到 `ACCESS_DENIED`）
- [ ] Service Token 透传 + `extract_st_prefix` 仅取前 8 位
- [ ] 私有计费/限流账本就绪
- [ ] （可选）`quota;check` 前置配额 + 聚合降级链
- [ ] 明确告知调用方：本端点是商业实体，与 demo 示范端点无关

## 3. 共享价值底座（每站都自动继承）

下述设计红利**你在任何一站都自动拥有**，故各站只讲增量收益：

- **统一操作语言**：`AI:<域>;<动作>,<参数>` 一种语法贯穿本地工具 / web API / 容器 / nocode / mesh 多跳。学一次，处处用。
- **减少工具选择的推理开销**：指令解析与 dispatch 是纯 stdlib 关键词/向量匹配，将工具匹配从推理层下沉到协议层；响应单行结构化（rst_err 字段），显著降低工具选择对上下文的占用（相比逐工具加载完整 JSON Schema）。
- **声明式即沙箱（指令/路径层）**：数据永远在参数位、指令在指令位，注入载荷无法逃逸——指令与路径层无需事后加固、无需自建沙箱。但 Copilot / skill_bridge 的 subprocess 执行面不在此列，必须按 `whitelist.json` 白名单 + 参数正则校验防护，不可省略（详见 [包开发指南 §6.2] 白名单闸门）。
- **端点无关 / 治理无关**：协议从不写死任何部署，去中心化下各角色可自托管、自运营，无需依赖任何中心节点。
- **渐进式采用（A0–A9）**：从零配置本地到自建 endpoint，升级是加法不是替代。

> 更多贯穿各站的能力（多语言别名、异步与跨节点、失败诊断、可观测端点）见速查表。

## 4. 沿途发现的联邦 mesh

当你在 **2.3 私有运行时** 阶段部署了自己的运行时，并开始把它连到别的运行时/端点（或让别人连你），你会自然碰上**跨节点编排**的需求——比如「用我本机的 A 能力，串接远端伙伴的 B 能力」。

那一刻，**联邦 mesh** 的价值才真正显现：
- 你不需要自己搭跨节点管道——同一套 `AI:` 语法即可触达远端能力，mesh 多跳按 `peer_credentials` 在节点间注入凭证；
- 多节点联邦按 peer 注入凭证，SQLite 缺失时自动降级为无凭证转发 + WARNING，不会因单点缺失而整体失败；（注意：此"无凭证转发"为**可用性优先**降级、**非安全推荐**，安全提示见 §2.4「配额 / 限流 / 降级」表后说明。）
- 对调用方而言，跨节点和本地调用是同一体验（见 2.1 的「一个入口收敛多提供方」）。

换句话说，mesh 不是一份「先读完的特性清单」，而是你**走到需要连外部节点时，才发现已经有人替你铺好的路**。它与 2.4 指令集成服务商天然互补：端点做跨组织结算入口，mesh 做跨节点能力编排。

## 5. 生态层镜头：价值如何交换（结算边界）

前面四站是**单个参与者怎么走**；这一节是**多人之间怎么换**——它不属于某一站，而是贯穿整条链之上的生态规则。

- **结算边界**：任何角色的变现/计费都走私有约定（Access/Service Token），项目不统一定价、不提供生态货币。
- 公共端点（`test.text-cli.com` / `api.text-cli.com`）仅为非盈利示范，与上述任何商业行为无财务绑定。
- 运行时不读取仓库 `registry/` 目录做 dispatch（那是格式模板，非语义注册表）。
- **`registry/` 是格式模板，不是实时服务目录**：仓库内的 `instructions.json` 和 `endpoints.json` 仅用于展示注册表的 JSON schema 和格式规范。生态参与者可参考这些模板设计自己的端点注册表——格式与 `/text-cli/skills` 响应结构一致，可直接作为端点能力声明的参照。

## 6. 机制速查

| 角色（成长顺序） | 需了解的核心机制 | 一站核心能力 |
