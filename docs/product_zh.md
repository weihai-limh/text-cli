## 一、你被什么困扰

AI 需要使用工具——只用推理解决不了计算、查天气、搜地图这类需要确定性的机械任务。

但现在调用工具的方式太重：每件工具都要占用上下文去读它的 JSON Schema、理解参数语义。工具越多，上下文越膨胀。

更糟的是，AI 发现工具的能力是被动式的——只能匹配上下文中已暴露的工具。一个端点还有什么工具可以用，不提前告诉 AI 就不知道。

收口：**AI 需要工具，但调用太重、发现太被动。**

---

## 二、text-cli 解决什么

text-cli 是**分布式指令分发骨架**。部署到一台机器后，这台机器上的服务和工具作为"能力源"对外提供能力。

就像魔法卷轴：你不必有运行高级魔法的魔力。撕开它，能力源为你的魔法释放赋能。

任何人都能写指令包装到骨架上。任何 Web 在线服务（API、MCP、脚本）接进来就是一条或多条指令。在协议层，无论你是人、是 AI、在 webchat 里还是在 agent 里——同一个请求，同一个响应。

### 两根脊梁：分布式 + 渐进式

| | 分布式 | 渐进式 |
|---|---|---|
| 什么意思 | 多台机器各自部署，各自暴露不同的能力。换 IP 就是换能力源，调用方式不变 | 每级都是完整终点。升级是加法，不是替代 |
| 怎么体现 | `AI:text-cli;query` 在 A 机器返回翻译能力，在 B 机器返回地图能力——同一行指令，不同的能力清单 | A0 零部署 curl → A3 平台管理 → A6 小企业工具 → A9 全量聚合 |
| 对谁重要 | 家庭多机器、团队多节点、公网多 service 聚合 | 从花店老板到开发者的全谱系用户 |

## 四、你获得什么能力

**三种指令来源**——你的 text-cli 服务不只是"安装的包"在提供能力：

| 来源 | 说明 |
|------|------|
| **安装的指令包** | 四种格式——native（handler.py）、nocode（AI 帮封装）、aggregate（纯声明降级链）、path（步骤链）。通过 `text-cli;install` 安装 |
| **MCP 生态** | MCP server 的工具自动编译为 text-cli 指令——成千上万工具，一次配置，不写代码 |
| **copilot 代理** | 本机文件/Git/shell/终端操作——这些能力不走包安装，而是 copilot 暴露后通过协议层调度 |

所有来源在降级链中地位平等——调用方不关心一条指令来自 native handler、MCP bridge 还是 copilot 代理。

- **路径编排**：多条指令串联成链。管道闭包原则——路径只做编排和插值，文件 IO、API 调用、推理全部通过指令。条件和降级内建
- **分布式分发**：多台机器各自部署，各自暴露不同能力。换 IP 就是换能力源，调用方式 `AI:domain;action,params` 不变
- **聚合降级**：同一类能力有多个提供方时自动切换——tx-map 配额耗尽 → gd-map 顶上。调用方不感知
- **让 AI 帮你造指令**：不是"写代码包装指令"，是"告诉 AI 你要什么能力，AI 帮你封装"。NoCode 路径让花店老板也能把十年经验变成可调用的诊断服务

## 五、三种部署模式

| 模式 | 包含 | 适用场景 |
|------|------|---------|
| **本机模式** | 仅 copilot | 个人开发者，AI Agent 操作本机文件/Git/shell |
| **内网模式** | copilot + service | 家庭/团队内网，共享指令包，多台机器各自暴露能力 |
| **公网模式** | copilot + service + endpoint | 对外提供服务，Access Token 鉴权，多 service 聚合 |

升级是加法——公网模式的用户仍然可以 curl 本机 copilot。

### 三把能力的钥匙

| 钥匙 | 赋予的能力 | 场景 |
|:---|:---|:---|
| copilot（127.0.0.1） | 操作本机文件系统、shell、Git、终端 | "帮我把这份文档推送到 GitHub" |
| service（0.0.0.0） | 挂载指令包、暴露外部服务 | 内网部署翻译服务，局域网任何人都能 curl |
| endpoint（公网） | 鉴权+路由+转发+记账 | 给外部调用方签 Access Token，他只看到一个入口 |

**copilot 绑 127.0.0.1 不是配置差异——是安全边界。** copilot 仅本机可达，所以能安全地暴露终端操作（shell、Git）。service 绑 0.0.0.0，外部可达，禁止接触终端。这是设计红线。

### 分布式拓扑

多个 endpoint 节点各自独立运营，各自连接不同的 service 子集。同一个 service 可同时向多个 endpoint 开放能力——管理员精确控制哪些指令对外暴露：

```
公网用户 → A5-1（接 A3-1+A3-2）→ 地图 + 翻译能力
公网用户 → A5-2（接 A3-2+A3-3）→ 翻译 + 天气能力
内网用户 → A3-5（纯内网，不对外）→ 全部能力
```

不是"一个中心端点汇聚所有服务"。是"多对多——哪个端点暴露哪些能力，由部署者决定"。

## 六、三种接入方式

| 你是谁 | 你怎么接入 | 你能得到什么 |
|------|---------|------------|
| **API/Script 开发者** | 写 `@register(domain, action)` 包装既有函数 → 自动生成 schema.json → `AI:text-cli;install` | 既有 API/脚本/知识库变成可分发、可计费的 text-cli 指令包 |
| **非开发者** | 让 AI 帮你把经验写成结构化文档 → AI 帮你封装为指令 | 十年盆栽经验变成可调用的诊断服务，不写一行代码 |
| **AI Agent** | `text-cli;query` 发现能力 → `text-cli;install` 扩展工具箱 → `text-cli;pro` 发布技能 | 从"匹配已有菜单"到"自由组合工具"到"烧录新指令供自己和后来的 AI 复用" |

> AI 从执行者变成协作者。去执行第一步是查询可用能力。缺什么自己装。把一次发现烧录成永久可复用的资产。

## 七、与同类方案的对比

| 维度 | Function Calling | MCP | text-cli |
|---|---|---|---|
| 调用方式 | 模型推理选函数 | 客户端直连 MCP server | 文本协议，HTTP POST |
| 工具发现 | 上下文被动暴露 | 连接时列出 tools | query 指令主动搜索 |
| 多提供方降级 | 无 | 无 | aggregate 聚合降级 |
| 跨机器 | 无 | 单 server | 多机器各自部署，调用方式不变 |
| 非开发者参与 | 需要写代码 | 需要写代码 | AI 帮封装，Markdown 即可 |

核心差异：Function Calling 是"AI 帮你选工具"，MCP 是"客户端连服务器"，text-cli 是"同一把遥控器控制不同的能力源"。

## 八、开始用

> 开放指令包即将随正式版本发布。当前阶段，从源码部署是主要路径。

### 快速体验

```bash
# 空桩占位 — 正式版本发布后此处将替换为可 copy-paste 的免费包命令
```

部署后验证：

```bash
curl -X POST <端点>/text-cli/cli \
  -H "Content-Type: application/json" \
  -d '{"prompt":"AI:text-cli;query"}'
```

效果信号：返回当前运行时所有可用指令清单。换一台机器调同一行——能力不同，调用方式一样。

### 预设

| 主题 | 说明 |
|------|------|
| **开箱即用** | 预置指令直接可用 |
| **匿名模式** | 默认不需要 token。内网环境下 curl 即用 |
| **生产模式** | 三层防线（IP 黑名单 + Token 校验 + 限流）+ Access Token 鉴权 |

## 九、项目愿景

人和 AI 共用同一个遥控器。人发 `AI:天气;查询,明天,威海`，AI 也发同样的指令——不是"AI 用 API"和"人用界面"，是同一把遥控器，拿在谁手里都是它。

让每个人把经验变成指令，每台机器暴露出能力，每个 AI 用同一行指令调度世界。
